# 产品定义与范围

状态:`draft` · 最后更新:2026-09-21 · 上游依据:用户需求(本仓库初始化时提供)

## 1. 一句话定位

一款由手机 App 灵活控制的、支持多频段无线收发的、可接入 DeepSeek 进行智能分析的便携式射频工具。

## 2. 目标用户与场景

### 2.1 目标用户

| 角色 | 诉求 |
|---|---|
| 射频/嵌入式学习者 | 低门槛观察真实空口信号,理解 OOK/FSK 与协议结构 |
| 自有设备所有者 | 排查自家遥控器、门磁、传感器、无线开关的频点与协议 |
| **屏蔽室 / 实验室内的射频调试人员** | 需要一个**不受本机 2.4GHz 干扰**、可长时间稳定控制的有线通道 |

### 2.2 核心使用场景(来自需求)

- **S1 远程部署**:设备放在车内/背包中,接入现场路由器 Wi-Fi;人在远处用手机 App 远程控制扫频、解码、发射。
- **S2 近距调试**:手机与设备 BLE 直连,免配网,快速操作与实验。
- **S3 AI 分析闭环**:App 把捕获的信号特征上传 DeepSeek → 得到信号类型/协议/威胁等级 → App 依结论下发指令(发射响应、保存信号)。
- **S4 多模块切换**:用户在 App 内配置当前使用哪个射频模块(CC1101 / SI4463 / nRF24L01…),设备加载对应驱动。
- **S5 屏蔽室内有线控制(2026-09-20 新增)**:设备与手机用 **USB OTG 线直连**,控制链路**完全不走射频**。典型场景是操作 2.4GHz 模块——它**按产品配置以满功率 20dBm 发射**(2026-09-21 决策,见 §2.3),而**同一时刻本机的 Wi-Fi/BLE 会被自己的这个 20dBm 发射压掉**,无线控制通道必然断。USB 有线通道是这种情况下唯一能保持控制的路径。

### 2.3 使用环境:屏蔽室(2026-09-20 决策)

**产品的目标使用环境是射频屏蔽室。** 这一条改变了整份设计文档的多个前提,故单列:

| 维度 | 屏蔽室内 | 影响 |
|---|---|---|
| 法规约束 | 有意豁免(泄漏受屏蔽效能限制) | C-04 的合规门禁**从"产品验收门"降为"参考设计"**,见 §4 与合规文档 |
| 2.4GHz 发射 | **出厂即按满功率 20dBm / 100mW**(2026-09-21 决策) | **Q-03 关闭:2.4GHz 列入本期需求,M3 保留**;R-01 的**对外**干扰风险基本解除。⚠️ **不设"保守默认 10dBm、由用户手动提高"这一层** —— `policy.tx_power_cap_dbm` 与模块上限一致(20dBm),功率门从此**只防"超过模块/硬件能力"**,不再承担法规限幅职责(故本项的验证落在硬件能力上,见测试 TC-104) |
| 本机无线自扰 | **仍然存在** | ⚠️ 屏蔽室挡的是"内外互相干扰",**挡不住同壳体厘米级间距的自扰**。M3 以**满功率 20dBm** 发射时仍会压掉本机 Wi-Fi/BLE ⇒ **S5 的 USB 有线通道不是"锦上添花",而是 2.4GHz 场景下的必要通道** |
| 手机联网 | 手机在屏蔽室内**可能无蜂窝/Wi-Fi** | DeepSeek 分析会不可用 ⇒ **离线降级(F-09 的本地规则库兜底)必须真的可用**,不能只是文档上的一句"降级" |
| 物理在场 | 设备与手机同处一室 | USB 有线连接天然满足"操作者在场"这一前提 |

## 3. 功能需求

| ID | 需求 | 优先级 | 备注 |
|---|---|---|---|
| F-01 | 自动扫频:在**所装模块的真实频段(387–525MHz)**内快速扫描,检测 RSSI 超阈值的信号 | P0 | **范围已按 ADR-0001 §5.1 收敛**:原"119–1050MHz"不可实现,用户已决定不增补硬件。带外请求必须明确回报"扫不到"(A-06) |
| F-02 | RSSI 实时读取,用于信号检测与阈值触发 | P0 | |
| F-03 | 原始数据捕获:保留信号时序特征(OOK/FSK 原始码流) | P0 | 依赖 RMT / SPI 高速读取;**OOK 路径仅 M1(SI4463)可用**,见 §6.2 |
| F-04 | 信号解码:识别遥控器、传感器等协议 | P0 | 分两层:通用特征层 + 协议指纹库;**433MHz OOK 遥控器只能经 M1 捕获** |
| F-05 | 信号发射:发射信号,可模拟目标信号 | P0 | **屏蔽室内使用,合规门禁降级为参考**(§2.3);审计仍保留(A-05) |
| F-06 | 多模块兼容:按用户配置加载 CC1101 / SI4463 等驱动 | P0 | 每模块独立 SPI、独立天线 |
| F-07 | 手机 App 远程控制(Wi-Fi 经路由器) | P0 | |
| F-08 | 手机 App 近距控制(BLE 直连) | P1 | **仅 Android**(C-06);iOS 已放弃 |
| **F-11** | **手机 App 有线控制(USB,经 OTG 线)** | **P0** | **2026-09-20 新增**。手机作 USB 主机、设备作 CDC-ACM 从设备;用途是**在 2.4GHz 模块发射时保持控制通道**(§2.2 S5)。与 Wi-Fi/BLE **共用同一套协议语义**,不新增消息类型。⚠️ 术语:用户侧叫"OTG",固件侧**不用** USB-OTG 外设(见 C-10/ADR-0003) |
| F-09 | DeepSeek 智能分析(类型/协议/威胁等级) | P1 | 在 App 侧调用;**屏蔽室内可能无网,离线兜底必须可用** |
| F-10 | 依 AI 结论回下发动作指令(发射/保存) | P1 | 发射仍需人工二次确认 |

### 3.1 明确不做(非目标)

- ❌ 不做通用频谱分析仪(无扫频前端/无校准功率测量)
- ❌ 不承诺解调任意未知协议;只做**已知协议指纹 + 通用特征描述**
- ❌ 不做 GSM/LTE/Wi-Fi 数据包解码(2.4GHz 部分仅做能量与 nRF 私有包)
- ❌ 不绕过任何加密或访问控制
- ❌ 不做发射功率的精确标定(仅档位控制)

> **Q-03 已关闭(2026-09-20)**:2.4GHz **列入本期需求**,M3(nRF24L01P + RFX2401C)保留。这与上面第 3 条非目标**不矛盾**——保留了 2.4GHz **硬件与能量/nRF 私有包能力**,但仍**不做** Wi-Fi/蓝牙数据包解码。

| C-02 | 每个射频模块独占 SPI 与天线 | 决定引脚预算与共存干扰模型 |

| C-04 | ~~发射必须合规(频段白名单 + 功率上限)~~ → **降级为参考设计**(2026-09-20):产品在**屏蔽室内**使用,法规约束有意豁免 | 门禁结构**保留**(纵深防御、防误操作),但**不再是产品验收门**。见 §2.3 与合规文档 |
| C-05 | 设备放置远处时无人值守 | 需要看门狗、状态恢复、超时保护 |
| **C-06** | **App 仅支持 Android**(2026-09-20 决策) | 删除 iOS 全部约束;可要求 HTTPS/`wss`、可依赖 Web Bluetooth,并**可依赖 WebUSB**(见 C-09) |
| **C-07** | ~~**设备端必须具备 OLED 显示屏**~~ → **⏸ 延期,不在本批开发**(2026-09-20 定为需求,**2026-09-21 决定延期**) | **不是取消**:引脚(GPIO40/41)与选型(I²C 4 针 SSD1306/SH1106)继续保留,见硬件文档 §2.5。但**本批不装、不写驱动**,因此它原本承担的三项职责(配对码显示 / AP 地址显示 / 本地状态出口)**在本批内没有载体** |

| **C-09** | **产品面向射频屏蔽室环境**(2026-09-20 决策) | 合规门禁降级为参考;**但自扰问题不消失** ⇒ USB 有线通道(F-11)成为必要能力;离线 AI 兜底必须可用 |
| **C-10** | **设备必须具备 USB 有线控制通道**(用户侧用普通 **OTG 线**连接,2026-09-20 决策,ADR-0003) | 实现上复用 ESP32-S3 内建 **USB Serial/JTAG** 的 CDC-ACM(硬件实现、零额外 BOM、保留 JTAG 调试)。⚠️ **注意术语**:用户侧说"OTG 连接"(指用 OTG 线把手机当 USB 主机),但**固件并不使用 USB-OTG 外设**——二者共用同一对 GPIO19/20 且互斥,用 OTG 需外接 PHY 或烧不可逆 eFuse 并失去 JTAG。详见 ADR-0003 |
| **C-11** | **2.4GHz 按满功率发射**(2026-09-21 决策) | `policy.tx_power_cap_dbm` 的 2.4GHz 口径取模块上限 **20dBm**;**不设保守默认值层**。理由:使用环境是屏蔽室(C-09),法规限幅已非设计输入。⚠️ **本项不自动推及 Sub-GHz**:M1/M2 的 433MHz 等频段的出厂 cap 是否也放开,仍是独立问题(见 NQ-03) |

## 6. 硬件选型(需求给定)

### 6.1 主控

**ESP32-S3N16R8** — Xtensa LX7 双核 240MHz,16MB Flash,8MB PSRAM,集成 2.4GHz Wi-Fi + BLE。

### 6.2 射频模块

| 编号 | 型号 | 芯片 | 频段 | 功率 | 接口/尺寸 | 特点 | 调制能力 |
|---|---|---|---|---|---|---|---|
| M1 | AS10-M4463D-SMA | Silicon Labs SI4463 | **425–525MHz**(官方手册,软件可调) | **100mW / 20dBm** | 4-Pin 硬件 SPI,24×16mm 直插 | 工业级,绕射及穿墙能力强,官方标称距离 2km;灵敏度 −126dBm@1kbps | **OOK/ASK + FSK 族**(SI4463 支持)⇒ **433MHz OOK 遥控器靠它** |
| M2 | AS07-M1101D-SMA | TI CC1101 | **387–464MHz**(官方手册,推荐 433±10MHz) | **10mW / 10dBm** | DIP 直插,28×15mm | 自带 FEC 与交织编码,抗干扰强,功耗低;灵敏度 −111dBm@1.2kbps | ⚠️ **官方手册只列 2-FSK / GFSK / MSK,无 OOK/ASK**(芯片本身支持 OOK,是模块未承诺) |
| M3 | AS01-ML01(**已确认,无后缀**) | Nordic nRF24L01P + **RFX2401C PA/LNA** | 2400–2525MHz(126 信道) | **约 20dBm / 100mW**(官方手册) | SPI,18×33.3mm 直插,SMA-K | 内建 LNA,6 通道数据;官方标称距离 2.0km;**带金属屏蔽罩** | GFSK |

> **制造商已确认**:三块均为**泽耀科技 / Ashining**(`ashining.com.cn`)。官方资料包已于 2026-09-20 完整取得,上表**全部为官方手册口径**;明细与"仍开放项"见 [`040-verified-platform-facts.md`](040-verified-platform-facts.md) F-4/F-4c。
>
> ⚠️ **M1/M2 的频段是模块级、不是芯片级**:SI4463 芯片可达 142–1050MHz、CC1101 芯片有三段,**但这两块模块的前端把能力裁掉了**。要覆盖更宽必须换/定制模块,不是换芯片版本。

> ⚠️ **一条会改变功能归属的硬约束**:M2(AS07-M1101D)的**官方模块手册**调制栏只列 **2-FSK / GFSK / MSK**,通篇无 ASK/OOK;其官方原文另称 2-FSK"与使用 ASK(AM)的简单遥控器不兼容"。而 M3(nRF24L01P)在 2.4GHz、与 433MHz OOK 无关。**因此 433MHz OOK 遥控器/传感器的捕获与复现,只能由 M1(SI4463)承担。** 这对 A-03 与需求 F-02 的实现路径有直接影响:OOK 相关的测试与验收必须绑定 M1,不能"随便用哪个模块"。
>
> **层级说明(避免误读为物理限制)**:随模块资料包取得的 **TI CC1101 数据手册明确支持 "OOK and flexible ASK shaping"**。所以这是**模块级官方口径的缺口**(厂商未列出/未承诺),不是"CC1101 芯片做不到"。若日后需要 AS07 做 OOK,须先向厂商确认固件/寄存器是否放开。

> ⚠️ 覆盖空白:**已决定接受**(ADR-0001 §5.1,不增补硬件)。三模块实际只覆盖 **387–525MHz(约占 119–1050MHz 的 15%)+ 2.4GHz**;119–300 / 525–779 / 928–1050MHz **物理上不可及**(见 C-08)。**强制义务**:带外请求必须"可见地失败",禁止让界面显示"无信号"——见 ADR-0001 §5.3 与判据 A-06。

### 6.3 控制通道(三条,2026-09-20 起)

| 通道 | 角色 | 抗本机 2.4GHz 自扰 | 备注 |
|---|---|---|---|
| Wi-Fi(WebSocket) | 远程 / 高吞吐(S1) | ❌ 会被压掉 | 需要现场路由器或设备 AP |
| BLE | 近距免配网、首次配网(S2) | ❌ 会被压掉 | 仅 Android |
| **USB(CDC-ACM over OTG)** | **2.4GHz 发射时的保底通道**(S5)、首次配对 | ✅ **有线,不受射频影响** | 复用 ESP32-S3 **内建 USB Serial/JTAG**(硬件实现,**无需额外芯片**);详见 ADR-0003 |

> **为什么 USB 是"必要"而不是"可选"**:M3 的 RFX2401C 以 20dBm 发射时,同壳体、厘米级间距的自扰会压掉本机 Wi-Fi/BLE。这意味着**用无线通道去控制 2.4GHz 发射,会在最需要中止能力的时候失去中止能力**。USB 有线通道消除了这个死结(判据 A-07)。

### 7.1 无屏带来的职责缺口(2026-09-21)

OLED 延期不等于这三项职责消失,只是**本批没有载体**。逐项给出"本批状态"与"最小替代":

| 原 OLED 职责 | 本批状态 | 最小替代(零新增 BOM) | 代价 |
|---|---|---|---|
| 显示 6 位一次性 `pair_code` | ❌ **无载体** | ① 改走 **USB 配对**;② 出厂随机码**印在机身标签**;③ **LED 计数序列**播放 | 见 §8 的三方案权衡 |
| 显示 AP 的 SSID 与地址 | ❌ **无载体** | AP 的 SSID 固定规则(含 `device_id`)、地址固定 `192.168.4.1` | 用户需查文档;`device_id` 仍可从机身标签读到 |

## 8. 首次配对的替代路径(无屏条件下,NQ-01)

`pair_code` 的作用是**防中间人**:BLE 配对若被截获,攻击者拿不到"设备端生成、需人工搬运"的那 6 位数字。**因此它的搬运通道必须与 BLE 不同源**——这正是无屏时的难点。三个候选:

| 方案 | 做法 | 优点 | 代价 / 风险 |
|---|---|---|---|
| **A. USB 配对为主(推荐)** | 首次配对**走 USB 线**(已由 C-10/F-11 保证);USB 是物理端口,天然满足"操作者在场",**结构上不需要 `pair_code`** | 零新增 BOM;安全性论证最强;顺手解决 AP 地址问题 | 每次首次配对都要拔插线;BLE 路径本批不具备配对能力 |
| **B. 标签固定码** | 出厂为每台设备生成随机 6 位码,印在机身标签;用户从标签抄入 | 实现最简,无需屏 | **码是静态的** ⇒ 失去"一次性"性质,防中间人强度下降(拿到设备/照片的人即拿到码) |
| **C. LED 计数序列** | 进入配对模式后,用已有 GPIO38 的 LED 逐位播放 6 位码 | 复用已有 BOM | **可读性差、易错**;需要额外定义"播放/分隔/重播"时序,且现场判断"播到第几位"很脆弱 |

**建议:A 为设计路径,B 仅在 A 不可用时作为临时兜底;不推荐 C。** 若采纳 A,契约 §7.1(1) 需补一句"USB 链路上 `pair_code` 不作为必要条件",并在测试计划里补一条"USB 配对本批必须可用"的零容忍用例。
