# 产品定义与范围

状态:`draft` · 最后更新:2026-09-21 · 上游依据:用户需求(本仓库初始化时提供)

## 1. 一句话定位

一款由手机 App 灵活控制的、支持多频段无线收发的、可接入 DeepSeek 进行智能分析的便携式射频工具。

## 2. 目标用户与场景

### 2.1 目标用户

| 角色 | 诉求 |
|---|---|
| 射频/嵌入式学习者 | 低门槛观察真实空口信号,理解 OOK/FSK 与协议结构 |
| 自有设备所有者 | 排查自家遥控器、门磁、传感器、无线开关的频点与协议 |
| **屏蔽室 / 实验室内的射频调试人员** | 需要一个**不受本机 2.4GHz 干扰**、可长时间稳定控制的有线通道 |

### 2.2 核心使用场景(来自需求)

- **S2 近距调试**:手机与设备 BLE 直连,免配网,快速操作与实验。⏸ **2026-09-21:本批不实现(BLE 移出本批,见 §2.5)** —— 场景定义与编号**保留**,留待后续批次。
- **S3 AI 分析闭环**:App 把捕获的信号特征上传 DeepSeek → 得到信号类型/协议/威胁等级 → App 依结论下发指令(发射响应、保存信号)。
- **S4 多模块切换**:用户在 App 内配置当前使用哪个射频模块(CC1101 / SI4463 / nRF24L01…),设备加载对应驱动。
- **S5 屏蔽室内有线控制(2026-09-20 新增)**:设备与手机用 **USB OTG 线直连**,控制链路**完全不走射频**。典型场景是操作 2.4GHz 模块——它**按产品配置以满功率 20dBm 发射**(2026-09-21 决策,见 §2.3),而**同一时刻本机的 Wi-Fi/BLE 会被自己的这个 20dBm 发射压掉**,无线控制通道必然断。USB 有线通道是这种情况下唯一能保持控制的路径。

> ⚠️ **`S1 远程部署`(无人值守)已于 2026-09-21 取消 —— 见 §2.4**。
> `S2`–`S5` **保留原编号不回填**(`S1` 这个号永久空缺),以免破坏其他文档中已有的引用;引用场景时请一律写成 `S1–S5` 或逐个点名,**不要**因为"只有四个了"就把 S5 说成 S4。

### 2.3 使用环境:屏蔽室(2026-09-20 决策)

**产品的目标使用环境是射频屏蔽室。** 这一条改变了整份设计文档的多个前提,故单列:

| 维度 | 屏蔽室内 | 影响 |
|---|---|---|
| 法规约束 | 有意豁免(泄漏受屏蔽效能限制) | C-04 的合规门禁**从"产品验收门"降为"参考设计"**,见 §4 与合规文档 |
| 2.4GHz 发射 | **出厂即按满功率 20dBm / 100mW**(2026-09-21 决策) | **Q-03 关闭:2.4GHz 列入本期需求,M3 保留**;R-01 的**对外**干扰风险基本解除。⚠️ **不设"保守默认 10dBm、由用户手动提高"这一层** —— `policy.tx_power_cap_dbm` 与模块上限一致(20dBm),功率门从此**只防"超过模块/硬件能力"**,不再承担法规限幅职责(故本项的验证落在硬件能力上,见测试 TC-104) |
| 本机无线自扰 | **仍然存在** | ⚠️ 屏蔽室挡的是"内外互相干扰",**挡不住同壳体厘米级间距的自扰**。M3 以**满功率 20dBm** 发射时仍会压掉本机 Wi-Fi/BLE ⇒ **S5 的 USB 有线通道不是"锦上添花",而是 2.4GHz 场景下的必要通道** |
| 手机联网 | 手机在屏蔽室内**可能无蜂窝/Wi-Fi** | DeepSeek 分析会不可用 ⇒ **离线降级(F-09 的本地规则库兜底)必须真的可用**,不能只是文档上的一句"降级" |
| 物理在场 | 设备与手机同处一室 | USB 有线连接天然满足"操作者在场"这一前提 |
| 无人值守 | **不成立(2026-09-21 取消)** | 见 §2.4:设备与操作者始终同室,因而不存在"设备单独留在现场"这一使用方式 |

### 2.4 取消「无人值守远程部署」(2026-09-21 决策)

原场景 `S1 远程部署`(设备置于车内/背包、人远处经现场路由器 Wi-Fi 远程操作)**已取消**。取消后的设计前提收缩为一句:

> **设备与手机同处一室,操作者在场,并在操作期间与设备保持连接。**

这条取消带来的影响:

| 项 | 影响 |
|---|---|
| 远程/无人值守监控 | ❌ 不再是需求。不再需要"设备独自挂机数小时"这一使用方式 |
| 设备侧离线记录 → 回读 | ❌ **不再是需求**(它原本只为"App 不在场"服务)。见 §7 待决问题表中的 **`Q-09(产品视角)`** 关闭记录 |
| WebSocket 通道的用途 | ⚠️ 由"**远程**(设备在另一处)"收窄为"**同室**高吞吐"。⚠️ 由此产生一个**待决问题 NQ-04**:USB 已是主通道后,Wi-Fi/WebSocket 是否仍值得为其维护全套实现。**该问题已由 §2.5 关闭** |
| **看门狗 / 超时保护 / 断线回 idle** | ✅ **全部保留,一个都不能省**。它们原本被写成"为无人值守服务",但**真实职责从来不是无人值守**,而是"**防止设备在失去控制链路后仍留在发射态**"。取消无人值守使这个要求**更重要**了 |

> 🔴 **本节最容易被误读为"这些保护可以删了"的地方**:"取消无人值守"**不是**"取消安全网"。恰恰相反 —— 既然每次操作都有人在场且连了线,**"断连必须立刻结束发射"就从事后补救变成了首要防线**。验证项 TC-054 已按此强化。

### 2.5 本批只做 USB 有线控制(2026-09-21 决策)

**决策:BLE 与 Wi-Fi 移出本批,本批控制通道只有 USB 一条。见 [ADR-0005](../adr/0005-usb-only-batch-and-deferred-wireless.md)。**

#### 2.5.1 ⚠️ 这是"移出本批",不是"从产品中取消"(最易被误读之处)

| | 延期(本决策) | 取消(本决策**不是**) |
|---|---|---|
| 固件本批是否实现 | ❌ 不实现 | ❌ 不实现 |
| 场景/需求定义是否保留 | ✅ **保留** | ❌ 删除 |
| 契约的承载章节(BLE 分片、`ble_frame_max` 推导、Wi-Fi/WebSocket 行) | ✅ **原样保留** | ❌ 删除或改为非目标 |
| schema 字段(`ble_frame_max` / `ble_frag_total_max`) | ✅ **保留** | ❌ 删除(且属不兼容变更) |
| 后续批次是否要做 | ✅ **要做** | ❌ 不做 |

**为什么必须保留能力定义**:契约是**传输无关**的(§1"一份帧格式,三条传输"),而 §2.2.1 那段 `ble_frame_max` 推导是**一次已完成且修正过两处口径错误的推导**。删掉它,下次纳入无线时要**重新推一遍并很可能重蹈原错**;而保留一个"本批不使用但已定义"的字段**成本为零**。技术上这也意味着**本决策不产生任何契约字段级不兼容变更**。

#### 2.5.2 本批的通道与场景归属

| 项 | 本批状态 |
|---|---|
| **USB 有线控制(F-11 / S5)** | ✅ **本批唯一控制通道**,首次配对的**唯一**路径 |
| BLE(`S2` / F-08) | ⏸ 移出本批(定义保留) |
| Wi-Fi / WebSocket(F-07) | ⏸ 移出本批(定义保留)。⚠️ 因此 **PWA 上 `wss://` 信任模型这一整块难题在本批根本不会出现** |
| `SET_NET` 配网 / 设备 AP | ⏸ 随 Wi-Fi 一并移出本批 |
| LED 本地指示 | ⚠️ 见 §7.1:载体**只剩板载 WS2812**(GPIO48,✅ 已核实;蜂鸣器不存在) |

#### 2.5.3 🔴 本决策的真实代价:控制通道塌缩为**单点**

取消 BLE 与 Wi-Fi **之前**,`R-01`(2.4GHz 自扰压掉无线)的失效模式是"无线断了,**USB 还在**"—— USB 是**保底**通道。
取消之后,**USB 不再有保底对象**:一旦它不可用,设备**完全无法被指挥,包括"中止发射"这条安全动作**。

> 因此 **`R-13`(PWA 能否经 WebUSB 访问该 CDC 设备)的影响从"失去保底"升级为"失去全部控制与配对能力"**,而 **A-07 的失败不再有替代方案**。处置见 §8.1 与 ADR-0005 §4 —— **该实测已升为发布门禁**。

#### 2.5.4 本批暴露给手机的 USB 是**两个设备**,不是"一个 USB 口"

⚠️ 这是本次核实出的硬件事实(见 [`040-verified-platform-facts.md`](040-verified-platform-facts.md) **F-4d**):开发板板载 **CH334 HUB**,同一个 Type-C 口下枚举出**两个独立 USB 设备** —— ESP32-S3 **原生 USB**(GPIO20/19)与 **CH343 USB 转 UART**(接 UART0:GPIO43/44)。

- 控制通道选定**原生 USB**(ADR-0005 §2.4):零额外器件、不占 UART0、保留 JTAG。
- ⚠️ **由此产生一条实现要求**:WebUSB 的设备过滤器**不能只用"通用 CDC"**(`classCode:2`),否则 CH343 会一并被选中,用户在设备选择界面里**没有可靠依据判断该选哪个**。**必须用精确的 `vendorId`/`productId`**(原生 USB = Espressif `0x303a`;CH343 = WCH `0x1a86`)。确切 PID **待实测**(F-6 的 V-12)。

| F-04 | 信号解码:识别遥控器、传感器等协议 | P0 | 分两层:通用特征层 + 协议指纹库;**433MHz OOK 遥控器只能经 M1 捕获** |

| F-09 | DeepSeek 智能分析(类型/协议/威胁等级) | P1 | 在 App 侧调用;**屏蔽室内可能无网,离线兜底必须可用** |
| F-10 | 依 AI 结论回下发动作指令(发射/保存) | P1 | 发射仍需人工二次确认 |

### 3.1 明确不做(非目标)

- ❌ 不做通用频谱分析仪(无扫频前端/无校准功率测量)
- ❌ 不承诺解调任意未知协议;只做**已知协议指纹 + 通用特征描述**
- ❌ 不做 GSM/LTE/Wi-Fi 数据包解码(2.4GHz 部分仅做能量与 nRF 私有包)
- ❌ 不绕过任何加密或访问控制
- ❌ 不做发射功率的精确标定(仅档位控制)

> **Q-03 已关闭(2026-09-20)**:2.4GHz **列入本期需求**,M3(nRF24L01P + RFX2401C)保留。这与上面第 3 条非目标**不矛盾**——保留了 2.4GHz **硬件与能量/nRF 私有包能力**,但仍**不做** Wi-Fi/蓝牙数据包解码。

## 4. 关键约束

| ID | 约束 | 影响 |
|---|---|---|
| C-01 | 主控固定为 ESP32-S3N16R8(16MB Flash / 8MB PSRAM) | 决定可用外设与内存预算 |
| C-02 | 每个射频模块独占 SPI 与天线 | 决定引脚预算与共存干扰模型 |
| C-03 | 必须免焊接(模块直插/排针) | 决定 BOM 与载板形态 |
| C-04 | ~~发射必须合规(频段白名单 + 功率上限)~~ → **降级为参考设计**(2026-09-20):产品在**屏蔽室内**使用,法规约束有意豁免 | 门禁结构**保留**(纵深防御、防误操作),但**不再是产品验收门**。见 §2.3 与合规文档 |
| ~~C-05~~ | ~~设备放置远处时无人值守~~ → **已取消(2026-09-21,用户)** | **无人值守远程部署不再是需求**(`S1` 取消,见 §2.4)。⚠️ **但它的三条工程手段一条都不删** —— 看门狗、状态恢复、超时保护的目标被重新表述为"**防止设备在无控制链路时滞留在发射态**"。这个目标不依赖无人值守,反而在"操作者始终在场"的前提下更要紧(见 TC-054) |
| **C-06** | **App 仅支持 Android**(2026-09-20 决策) | 删除 iOS 全部约束;可要求 HTTPS/`wss`、可依赖 Web Bluetooth,并**可依赖 WebUSB**(见 C-09) |
| **C-07** | ~~**设备端必须具备 OLED 显示屏**~~ → **⏸ 延期,不在本批开发**(2026-09-20 定为需求,**2026-09-21 决定延期**) | **不是取消**:引脚(GPIO40/41)与选型(I²C 4 针 SSD1306/SH1106)继续保留,见硬件文档 §2.5。但**本批不装、不写驱动**,因此它原本承担的三项职责(配对码显示 / AP 地址显示 / 本地状态出口)**在本批内没有载体** |
| **C-08** | **频段覆盖固定为所装模块能力(387–525MHz + 2.4GHz),不增补硬件**;119–300 / 525–779 / 928–1050MHz **不在范围内**(2026-09-20 决策,ADR-0001 §5.1) | 禁止在文档/UI/宣传中暗示可覆盖带外频段;带外请求必须**可见地失败**(A-06) |
| **C-09** | **产品面向射频屏蔽室环境**(2026-09-20 决策) | 合规门禁降级为参考;**但自扰问题不消失** ⇒ USB 有线通道(F-11)成为必要能力;离线 AI 兜底必须可用 |
| **C-10** | **设备必须具备 USB 有线控制通道**(用户侧用普通 **OTG 线**连接,2026-09-20 决策,ADR-0003) | 实现上复用 ESP32-S3 内建 **USB Serial/JTAG** 的 CDC-ACM(硬件实现、零额外 BOM、保留 JTAG 调试)。⚠️ **注意术语**:用户侧说"OTG 连接"(指用 OTG 线把手机当 USB 主机),但**固件并不使用 USB-OTG 外设**——二者共用同一对 GPIO19/20 且互斥,用 OTG 需外接 PHY 或烧不可逆 eFuse 并失去 JTAG。详见 ADR-0003 |
| **C-11** | **所有模块按满功率发射**(2.4GHz 于 2026-09-21 决策;Sub-GHz 于同日 **NQ-03 关闭**后一并适用) | "满功率"的定义是**每个模块自己的 `tx_max_dbm`**,不是一个统一数字:`policy.tx_power_cap_dbm` 取**设备全局最大值 20dBm**,逐次发射的有效上限 = `min(请求值, 全局 cap, 该模块 tx_max_dbm)` ⇒ M1/M3 可用到 **20dBm**,**M2(AS07)仍是 10dBm**——因为模块硬件只到 10dBm,不是被策略限住。**不设保守默认值层**。理由:使用环境是屏蔽室(C-09),法规限幅已非设计输入 |
| **C-12** | **发射功率必须可由用户在 App 内调节**(2026-09-21 决策,与 C-11 配套) | 出厂默认 = 满功率(C-11),但**默认值不等于固定值**:App 必须提供按模块的功率选择(步进不超过 1dB),并显示**本次实际生效值**。理由:降低功率是**唯一不需要换硬件即可控制自扰(R-01)与近场饱和的手段**,把它锁死在 20dBm 会移除这个手段。⚠️ **降低不需要额外确认,提高才需要**(并在确认弹窗展示生效值);设备回 `TX_STATUS` 时必须回报 `granted_power_dbm` |

## 8. 首次配对的替代路径(无屏条件下,NQ-01)

`pair_code` 的作用是**防中间人**:BLE 配对若被截获,攻击者拿不到"设备端生成、需人工搬运"的那 6 位数字。**因此它的搬运通道必须与 BLE 不同源**——这正是无屏时的难点。三个候选(**已定案为 A,见 §8.1**):

| 方案 | 做法 | 优点 | 代价 / 风险 |
|---|---|---|---|
| **A. USB 配对为主(✅ 已定案)** | 首次配对**走 USB 线**(已由 C-10/F-11 保证);USB 是物理端口,天然满足"操作者在场",**结构上不需要 `pair_code`** | 零新增 BOM;安全性论证最强;顺手解决 AP 地址问题 | 每次首次配对都要拔插线;BLE 路径本批不具备配对能力(⇒ 依赖 WebUSB 实测通过,见 §8.1 末注) |
| **B. 标签固定码** | 出厂为每台设备生成随机 6 位码,印在机身标签;用户从标签抄入 | 实现最简,无需屏 | **码是静态的** ⇒ 失去"一次性"性质,防中间人强度下降(拿到设备/照片的人即拿到码) |
| **C. LED 计数序列** | 进入配对模式后,用**板载 WS2812** 逐位播放 6 位码 | 复用已有器件(板载 WS2812) | **可读性差、易错**;需要额外定义"播放/分隔/重播"时序,且现场判断"播到第几位"很脆弱。⚠️ 本批**只剩一颗灯**(无蜂鸣器),比原评估更弱。🔴 **且 2026-09-21 起该方案还多一道硬门槛**:指示灯**不得承载任何凭据**(C-04 红线,见硬件文档 §2.7 纪律 2)——**若把 `pair_code` 编码进灯光,本方案直接违规** |

### 8.1 定稿(2026-09-21,用户选 **方案 A**)

**本批首次配对只走 USB。** 由此产生的契约级结论(已写入契约 §7.1(1)):

| # | 定稿内容 | 含义 |
|---|---|---|
| 1 | **USB = 可信配对信道**,且是本批唯一路径 | `pairing_secret` 只经 USB 下发;USB 上线后的 `HELLO{pairing:true}` **不要求** `pair_code` |
| 2 | **无线链路本批不承担配对职责** | ⚠️ **2026-09-21 收窄**:BLE 与 Wi-Fi 已**移出本批**(§2.5),故本批**不存在**"在无线链路上请求配对"这一情形。契约中 `no_display` / `ble_only` 两个错误码**本批均为无活路径的保留值**,留给后续批次 —— **不要**为它们造路径或用例 |
| 3 | **`pair_code` 字段保留但本批不校验** | 保留是为了下一批 OLED 到位后启用,不是为了"本批可用" |
| 4 | **本批没有"链路选择",只有唯一链路** | ⚠️ **2026-09-21 修正**:原文为"配对完成后,三条链路在命令能力上等价" —— 该表述**随 §2.5 失效**(本批只实现 USB)。后续批次重新纳入无线时,此条恢复为"三条链路命令能力等价" |

> ⚠️ **不可让步的两条**(选 A 不会豁免它们):
> - **重新绑定必须设备端物理按键确认** —— USB 的在场性**替代不了**这条。USB 防的是"远距离截获配对",防不了"别人趁你不在插线改绑"。
> - **`pairing_secret` 的载体绝不能是人眼可读的**(屏 / 标签 / LED 编码)。A 方案之所以成立,恰恰是因为 USB 不是人眼信道。
>
> ⚠️ **本批由此产生一个阻塞级依赖(2026-09-21 升级)**:首次配对现在**必须**经 USB,而"Android Chrome 的 WebUSB 能否访问 CDC-ACM 设备"是**未实测项**(ADR-0003 USB-R1 / 测试 TC-074a)。若该项不通过,则**首次配对无路可走** —— 降级路径是原生 Android USB Host 小壳(见 App 文档 §1.2.1),不是"退回无码 BLE 配对"。
>
> 🔴 **取消无线后这条依赖更重了**:USB 原先是"保底通道",现在**是唯一通道**。因此该实测从"实现阶段第一项"升为**发布门禁** —— 它不通过则本批**既不能配对、也不能控制**(ADR-0005 §4)。

### 8.2 未采纳的备选(留档)

| 方案 | 为什么未采纳 |
|---|---|
| B. 标签固定码 | 码是**静态**的 ⇒ 失去"一次性"性质(拍照/短暂接触即永久泄露)。仅在 A 不可用时作临时兜底 |
| C. LED 计数序列 | 可读性差、需额外定义播放时序,现场判断"播到第几位"很脆弱。不推荐 |

> 两方案共同的问题:**它们都是"人眼信道"**,与上一节那条不可让步的红线相邻。A 方案绕开了这个性质问题,代价只是"首次配对要插一次线"。
