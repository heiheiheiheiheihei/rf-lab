# 跨平台 UI 规格 — Web / BLE / Android / uConsole

状态:现行 · 2026-11-21(官网同源视觉 + 交互终端) · 固件目标 **0.6.0** · 上游硬件与协议:[`00-mvp.md`](00-mvp.md)

> 一句话:**一块 ESP32-C3 同时开 Wi-Fi Web 和 BLE 外设;同一份单页 UI 既跑浏览器也跑 Android WebView;uConsole 用键盘 TUI 走同一套 HTTP 契约。** 串口与 OLED 的 0.5.0 行为不变。

## 1. 结论与边界

| 通道 | 入口 | 传输 | 是否需要装驱动 |
|---|---|---|---|
| Web(手机/PC/uConsole 浏览器) | `http://192.168.4.1/`(AP)或 STA IP | HTTP + SSE | 否 |
| Android APP | 安装 APK,扫描 `RF-Lab-*` | BLE GATT(自定义 NUS 风格) | 否 |
| uConsole 按键 | `rflab-tui`(SSH/本地终端) | HTTP;断网回退 USB 串口 | 否 |
| 串口(既有) | `/dev/ttyACM0` 115200 | 文本命令行 | 否 |
| OLED(既有) | 72×40 | 只读状态页 | — |

**不做**:云账户、远程公网访问、OTA、滚动码、频谱。Web/BLE 只复用 0.5.0 已有的固定码能力。

**代价(写死)**:

- Wi-Fi + BLE 同时开,ESP32-C3 的 2.4G 射频在两者间分时;**315/433 发射链路不受影响**(不同频段、不同芯片)。
- C3 只有 400KB SRAM。BLE 用 NimBLE(非 Bluedroid),HTTP 只保留 2 个 SSE 长连接,超出由 LRU 回收。
- Web 页面内嵌在固件里(gzip),改 UI 必须重新烧录;不引入 SPIFFS/LittleFS,避免多一个可损坏的文件系统。
- AP 只在回退/配网时打开,STA 成功时关闭;AP WPA2 密码固定在固件宏,换密码要重编。
- **BLE 无链路加密**,用 4 位应用层 PIN 补偿;PIN 在 OLED 开机页与串口 `PIN` 显示。这不是强安全边界。
- UI 的 `ARM` 只是**防误触**,不是发射硬门控;固件没有物理 RF_KILL(0.5.0 已如此)。
- **HTTP 无登录**:能连上 AP(WPA2)或同一 STA LAN 的人都能发码;AP 密码/局域网可达性是门槛。
- BLE 只做应用层 PIN,不加密链路;抓包者仍能看到明文命令。

## 2. 架构

```text
                    ┌──────────────────────── ESP32-C3 (0.6.0) ───────────────────────┐
  browser ──HTTP/SSE──▶ esp_http_server ─┐                                          │
  Android ──BLE GATT──▶ NimBLE (NimBLE) ─┼─▶ app_cmd queue ─▶ 既有 handle_line()    │
  uConsole ─HTTP/串口─▶ (same HTTP API) ─┘         │                 │                │
                                                   │                 ├─▶ UART1 → YS-RF34DL
  USB 串口 ───────────▶ console_read ──────────────┘                 ├─▶ NVS 码库
                                                                     └─▶ OLED 状态页
                                          app 快照(state/codes) ◀── 事件环(link ring)
                                                   │
                                          SSE / BLE 通知(分片)
```

- **单一控制面**:所有传输最终只提交一行既有命令(`SEND 1`、`LONG 1`…),不复制业务逻辑。
- **单一状态源**:`main.c` 仍是码库/计数器/模块状态的唯一所有者;Web/BLE 只读快照。
- **事件**:小型事件(LEARN/RX/TX/log)进环形缓冲;`state`/`codes` 快照按序号推送,避免 25Hz 长发心跳刷爆 BLE。
- **线程**:主循环执行命令、泵模块、刷 OLED;HTTP 与 BLE 各自任务只做入队/通知,不碰模块 UART。

## 3. Wi-Fi 与 HTTP

### 3.1 网络模式(STA 优先,AP 回退)

| 模式 | 含义 | AP |
|---|---|---|
| `ap` | 无凭据,或用户 `WIFI CLEAR` | 开 |
| `connecting` | 有凭据,启动时仅 STA,最长 15s | **关** |
| `sta` | STA 已连上局域网 | **关** |
| `apsta` | 连接失败回退,或在 AP 里重新配网 | 开 |

| 项 | 值 |
|---|---|
| AP SSID | `RF-Lab-XXXX`(MAC 末两字节) |
| AP 密码 | `rflab1234`(固件宏 `RFLAB_AP_PASS` 可改) |
| AP 地址 | `192.168.4.1` |
| STA | 凭据存 NVS 命名空间 `net`;SSID/PASS 由 Web、BLE 或串口写入 |
| 主机名 | `rf-lab` |
| 省电 | 关闭 modem sleep,保证 Web 响应 |

状态转换:

```text
无凭据 ──────────────────────────────▶ ap
有凭据 ──启动 STA-only──成功──▶ sta(局域网 IP)
                         └15s 失败──▶ apsta(AP + 后台重连)
sta 掉线 ────────────────────────────▶ apsta(AP 立即打开 + 退避重连)
ap/apsta 里配网 ──────────────────────▶ apsta(AP 保持,避免踢掉配网浏览器)
WIFI CLEAR ──────────────────────────▶ ap(删除凭据,STA 停止)
```

要点:

- 启动有凭据时 **AP 关闭**,15s 内拿不到 IP 才打开 AP;用户在失败后连 `RF-Lab-XXXX` 即可配网。
- AP 里配网成功**不关闭 AP**:正在配网的浏览器不会被踢;下次启动才回到 STA-only。
- `sta` 掉线后 AP 立即打开,后台按 5/10/20/30/60s 退避重连;`apsta` 下 AP 一直可用。
- `WIFI CLEAR` 删除 NVS 凭据并切回 `ap`;这是"忘记网络/强制 AP"的入口。
- 代价:失败时最多等 15s 才有 AP;APSTA 期间 AP 与 STA 同信道,吞吐/功耗略增。

### 3.2 HTTP API(v1)

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 单页 UI(gzip,内嵌) |
| GET | `/favicon.ico` | 204;图标用 HTML data URI,无额外请求 |
| GET | `/api/hello` | `{fw,proto,name,ap_ssid,ip,auth}` |
| GET | `/api/state` | 当前状态快照(§3.3) |
| GET | `/api/codes` | 码库数组 |
| GET | `/api/events` | **SSE**:`hello` / `state` / `codes` / `event` / `log` |
| POST | `/api/cmd` | body `{"cmd":"SEND 1"}` 或纯文本;202 入队 |
| POST | `/api/wifi` | `{"ssid":"...","pass":"..."}`;存 NVS 并尝试连接(AP 保持);202 |
| POST | `/api/wifi/clear` | 删除 STA 凭据,回 AP-only;202 |
| GET | `/api/net` | AP/STA 详情与 RSSI |

约定:

- JSON 一律 UTF-8、无 BOM;未知字段忽略。
- `POST` 只表示**入队成功**,执行结果通过 SSE `event`/`log` 返回。命令最长 96 字节,队列深度 8;满时 503。
- SSE 每 10s 发 `: ping`;客户端断开由发送失败检测。
- 响应头:`Cache-Control: no-store`;API 带 `Access-Control-Allow-Origin: *`(仅本地开发便利,不构成鉴权)。
- `GET /api/events` 首帧发 `hello`,随后在快照序号变化时推送 `state`/`codes`。

### 3.3 状态快照

```json
{
  "fw": "0.6.0", "proto": 1, "uptime_ms": 123456,
  "net": {"mode":"apsta","ap_on":1,"has_creds":1,
          "ap_ssid":"RF-Lab-AB12","ap_ip":"192.168.4.1",
          "sta_connected":true,"sta_ssid":"home","sta_ip":"192.168.1.50","rssi":-57},
  "ble": {"on":1,"conn":0,"name":"RF-Lab-AB12","pin_set":1},
  "module": {"baud":9600,"rx_bytes":296,"frames":37,"acks":0,"dups":3,
             "stray":0,"resync":0},
  "store": {"count":5,"max":32},
  "oled": {"present":1,"on":1,"flush":43,"err":0,"max_us":8747},
  "tx": {"active":0,"kind":"idle","id":0,"ok":0,"ms":0},
  "last": {"kind":"rx","id":2,"band":"315M","code":"5555033C","ms":123}
}
```

码库数组元素:`{"id":1,"band":"315M","code":"5555034C"}`。

事件对象(SSE `data`,或 BLE 一行):

```json
{"t":"event","seq":8,"kind":"learn","id":6,"band":"315M","code":"5555034C","line":"LEARN id=6 ..."}
{"t":"event","seq":9,"kind":"tx","tx":"send","id":1,"band":"315M","code":"...","ok":1,"ms":852,"line":"OK tx ..."}
{"t":"log","seq":10,"line":"OK mode=continuous"}
{"t":"state","seq":11,"data":{...}}
{"t":"codes","seq":4,"items":[...]}
{"t":"hello","fw":"0.6.0","proto":1,"name":"RF-Lab-AB12","auth":1}
{"t":"auth","ok":1}
```

`tx.kind`:`send|long|stop`;`tx.active=1` 表示长发进行中。`seq` 单调递增,溢出回绕不算错误。

## 4. BLE 协议

| 项 | 值 |
|---|---|
| 设备名 | `RF-Lab-XXXX` |
| Service | `5a3d0001-7c1f-4b8e-9a55-52464c414231` |
| RX(客户端写) | `5a3d0002-7c1f-4b8e-9a55-52464c414231` |
| TX(设备通知) | `5a3d0003-7c1f-4b8e-9a55-52464c414231` |
| 属性 | RX:WRITE / WRITE_NO_RSP;TX:NOTIFY |
| MTU | 首选 247;通知按 `MTU-3` 分片 |
| 编码 | UTF-8 行协议;`\n` 结束;客户端按 `\n` 重组 |
| 广播 | 连接模式 UND;广播名 + 128-bit Service UUID 在 scan response |

命令与 HTTP 相同,一行一条。鉴权:

1. 连接后设备发 `{"t":"hello",...,"auth":0}`。
2. 客户端发 `AUTH <4位PIN>`;成功 `{"t":"auth","ok":1}`,之后所有命令可用。
3. 未鉴权只接受 `AUTH`;连续 5 次错误断开并暂停广播 10s(实现为断开后由 `start_adv` 重新广播;暂停窗口未单独做)。
4. PIN 存 NVS(`ble_pin`),首次启动随机 4 位;OLED 开机页显示 5s;串口 `PIN` 可查。

PIN 是**应用层**,不改变 BLE 链路加密状态;抓包者仍能看到明文。它挡的是"隔壁随手连上就发码",不是有备而来的攻击者。

  `LAN MODE` / `AP FALLBACK` / `WIFI CONNECTING`,`FORGET / AP` 删除 STA 凭据。
- 所有动作都先本地回显 `> SEND 1`,再按 `event/log` 更新结果;失败不静默。
- 键盘可达 + `:focus-visible` 2px 琥珀;`aria-live=polite` 播报事件;对比度满足 WCAG AA。

## 9. 关键判断与避免的误修

1. **为什么所有传输只提交既有命令行,而不是各写一套 API?**
   0.5.0 的命令语义(尤其 `F0` 0.85s、`FE/FF`)已被上机验证;复制业务逻辑等于复制 bug。新增层只做"传输 → 一行命令 → 事件"。

2. **为什么 Web 用 SSE 而不是 WebSocket?**
   事件是单向、低频;SSE 是普通 HTTP,ESP-IDF 的 `httpd_resp_send_chunk` 足够,浏览器自动重连,Android WebView 也原生支持。省掉 WS 握手/掩码/分片代码与 RAM。

3. **为什么不把 UI 放 LittleFS?**
   单页 gzip 约 20KB,直接 `EMBED_FILES` 进 app 分区:少一个分区、少一种掉电损坏面、烧录即整体一致。代价是改 UI 要重烧,可接受。

4. **为什么 BLE 用 NimBLE 而不是 Bluedroid?**
   C3 只有 400KB SRAM,同时要 Wi-Fi + HTTP + 事件环。NimBLE 的 RAM/Flash 占用显著更小;代价是 API 更底层,需要自己写 GATT 表。

5. **为什么状态快照按序号推送,不把每次 ACK 都推?**
   长发心跳 ~25Hz;每次推 JSON 会把 BLE 带宽和手机电量吃光。代码只推**变化后的快照**(上限 5Hz),心跳只进计数器。

6. **为什么 ARM 默认关?**
   手机放在口袋里误触 `SEND` 会真的发码。ARM 是本地 UI 状态,不假装是安全机制;串口行为保持 0.5.0 不变。

7. **避免的误修**:
   - ❌ 把 Wi-Fi 凭据写死在源码:换网络要重编。→ NVS + Web 配网。
   - ❌ STA 连不上就关 AP:用户失去入口。→ 15s 失败后打开 AP 回退。
   - ❌ AP 里配网成功立刻关 AP:会踢掉正在配网的浏览器。→ 配网成功后保持 AP,下次启动再 STA-only。
   - ❌ BLE 用明文无 PIN:隔壁随手可发。→ 应用层 PIN + 失败退避。
   - ❌ 为省事把 OLED 状态页换成网络日志:72×40 放不下,且会破坏已验证的 0.5.0 页。→ 只加一行网络状态/开机 PIN 页。
   - ❌ 用 `deep sleep` 省电:会断 Wi-Fi/BLE,也丢模块 UART。→ 不做。

8. **为什么统一视觉,却不复用官网的 CSS/JS?**
   官网是 41KB HTML + 62KB CSS + 30KB JS 的滚动宣传页,带 Canvas 频谱、滚动揭示和配装器;
   固件单页受 2MB app 分区、80KB 级 gzip 预算与无外部请求约束。复用代码会把官网的
   交互与体积带进设备。**统一 token 与组件语法,不统一代码**:`site/style.css :root` 是色板/字体的
   唯一来源,`web/app.css` 复制值而不 `@import`;改版式各改各的,只有设备 UI 变化才重拍官网截图。

9. **避免的误修(视觉统一)**:
   - ❌ 为“看起来一样”把 `site/` 的 Canvas/滚动动画塞进 `web/`:挤占固件空间,且平板上无法滚动。
   - ❌ 把终端改成官网式长页面/导航:现场终端是一屏操作,滚动会遮住码库与 STOP。
   - ❌ 只改颜色不改组件语法(圆角/切角/角标/等宽标签):截图仍会像两套产品。
   - ❌ 复用官网截图当设备截图:截图来自 `tools/ui_mock_server.py`,必须标 `MOCK`。
