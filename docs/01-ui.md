# 跨平台 UI 规格 — Web / BLE / Android / uConsole / Watch

状态:现行 · 2026-11-22(码库 v2 + 官网同源视觉 + 交互终端 + 双槽 OTA + APP 自更新) · 固件目标 **0.7.1** · **0.7.3 一键固件更新为规划(§3.4.1)** · 上游硬件与协议:[`00-mvp.md`](00-mvp.md)

> 一句话:**一块 ESP32-C3 同时开 Wi-Fi Web 和 BLE 外设;同一份单页 UI 既跑浏览器也跑 Android WebView;uConsole 用键盘 TUI 走同一套 HTTP 契约。** 串口与 OLED 的 0.5.0 行为不变。

## 1. 结论与边界

| 通道 | 入口 | 传输 | 是否需要装驱动 |
|---|---|---|---|
| Web(手机/PC/uConsole 浏览器) | `http://192.168.4.1/`(AP)或 STA IP | HTTP + SSE | 否 |
| Android APP | 安装 APK,扫描 `RF-Lab-*` | BLE GATT(自定义 NUS 风格) | 否 |
| uConsole 按键 | `rflab-tui`(SSH/本地终端) | HTTP;断网回退 USB 串口 | 否 |
| 串口(既有) | `/dev/ttyACM0` 115200 | 文本命令行 | 否 |
| OLED(既有) | 72×40 | 只读状态页 | — |

**不做**:云账户、远程公网访问、滚动码、频谱。Web/BLE 只复用 0.5.0 已有的固定码能力。
OTA **做**,但只做设备固件(双槽 + Web/串口):**不更新 APK**、不做云推送、不做签名校验。
APK 的更新走另一条**客户端**路径:APP 查 GitHub Releases → 校验 → 系统安装器(§3.5),
与设备 OTA 完全无关,也不经过设备。

**代价(写死)**:

- Wi-Fi + BLE 同时开,ESP32-C3 的 2.4G 射频在两者间分时;**315/433 发射链路不受影响**(不同频段、不同芯片)。
- C3 只有 400KB SRAM。BLE 用 NimBLE(非 Bluedroid),HTTP 只保留 2 个 SSE 长连接,超出由 LRU 回收。
- Web 页面仍内嵌在固件里(gzip),不引入 SPIFFS/LittleFS;OTA 更新的是**整个 app 镜像**(含页面),双槽写入、可回滚。改 UI 后仍要重建/重烧一次才能进入首个 OTA 版本。
- OTA 端点**默认关闭**:只有串口 `OTA` 生成 8-hex token 后才接受上传;token 10 分钟、5 次错误锁定。它是应用层门,**不是签名/加密**,也没有 secure boot。
- AP 只在回退/配网时打开,STA 成功时关闭;AP WPA2 密码固定在固件宏,换密码要重编。
- **BLE 无链路加密**,用 4 位应用层 PIN 补偿;PIN 在 OLED 开机页与串口 `PIN` 显示。这不是强安全边界。
- UI 的 `ARM` 只是**防误触**,不是发射硬门控;固件没有物理 RF_KILL(0.5.0 已如此)。
- **HTTP 无登录**:能连上 AP(WPA2)或同一 STA LAN 的人都能发码;AP 密码/局域网可达性是门槛。
- BLE 只做应用层 PIN,不加密链路;抓包者仍能看到明文命令。
- **APP 自更新需要联网**:查 `api.github.com` 与下载 APK,离线/被限流时静默跳过;它不参与
  设备控制链路,失败不影响 BLE 功能。更新包由系统 `PackageInstaller` 安装并由系统验签。

## 2. 架构

```text
                    ┌──────────────────────── ESP32-C3 (0.7.1) ───────────────────────┐
  browser ──HTTP/SSE──▶ esp_http_server ─┐                                          │
  Android ──BLE GATT──▶ NimBLE (NimBLE) ─┼─▶ app_cmd queue ─▶ 既有 handle_line()    │
  uConsole ─HTTP/串口─▶ (same HTTP API) ─┘         │                 │                │
                                                   │                 ├─▶ UART1 → YS-RF34DL
  USB 串口 ───────────▶ console_read ──────────────┘                 ├─▶ NVS 码库
                                                                     └─▶ OLED 状态页
                                          app 快照(state/codes) ◀── 事件环(link ring)
                                                   │
                                          SSE / BLE 通知(分片)
```

- **单一控制面**:所有传输最终只提交一行既有命令(`SEND 1`、`LONG 1`…),不复制业务逻辑。
- **单一状态源**:`main.c` 仍是码库/计数器/模块状态的唯一所有者;Web/BLE 只读快照。
- **事件**:小型事件(LEARN/RX/TX/log)进环形缓冲;`state`/`codes` 快照按序号推送,避免 25Hz 长发心跳刷爆 BLE。
- **线程**:主循环执行命令、泵模块、刷 OLED;HTTP 与 BLE 各自任务只做入队/通知,不碰模块 UART。

## 3. Wi-Fi 与 HTTP

### 3.1 网络模式(STA 优先,AP 回退)

| 模式 | 含义 | AP |
|---|---|---|
| `ap` | 无凭据,或用户 `WIFI CLEAR` | 开 |
| `connecting` | 有凭据,启动时仅 STA,最长 15s | **关** |
| `sta` | STA 已连上局域网 | **关** |
| `apsta` | 连接失败回退,或在 AP 里重新配网 | 开 |

| 项 | 值 |
|---|---|
| AP SSID | `RF-Lab-XXXX`(MAC 末两字节) |
| AP 密码 | `rflab1234`(固件宏 `RFLAB_AP_PASS` 可改) |
| AP 地址 | `192.168.4.1` |
| STA | 凭据存 NVS 命名空间 `net`;SSID/PASS 由 Web、BLE 或串口写入 |
| 主机名 | `rf-lab` |
| 省电 | 关闭 modem sleep,保证 Web 响应 |

状态转换:

```text
无凭据 ──────────────────────────────▶ ap
有凭据 ──启动 STA-only──成功──▶ sta(局域网 IP)
                         └15s 失败──▶ apsta(AP + 后台重连)
sta 掉线 ────────────────────────────▶ apsta(AP 立即打开 + 退避重连)
ap/apsta 里配网 ──────────────────────▶ apsta(AP 保持,避免踢掉配网浏览器)
WIFI CLEAR ──────────────────────────▶ ap(删除凭据,STA 停止)
```

要点:

- 启动有凭据时 **AP 关闭**,15s 内拿不到 IP 才打开 AP;用户在失败后连 `RF-Lab-XXXX` 即可配网。
- AP 里配网成功**不关闭 AP**:正在配网的浏览器不会被踢;下次启动才回到 STA-only。
- `sta` 掉线后 AP 立即打开,后台按 5/10/20/30/60s 退避重连;`apsta` 下 AP 一直可用。
- `WIFI CLEAR` 删除 NVS 凭据并切回 `ap`;这是"忘记网络/强制 AP"的入口。
- 代价:失败时最多等 15s 才有 AP;APSTA 期间 AP 与 STA 同信道,吞吐/功耗略增。

### 3.2 HTTP API(v1)

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 单页 UI(gzip,内嵌) |
| GET | `/favicon.ico` | 204;图标用 HTML data URI,无额外请求 |
| GET | `/api/hello` | `{fw,build,ui,proto,codebook,name,ap_ssid,ip,auth}`;`build`=git 短哈希(+dirty),`ui`=页面构建号,`codebook:2`=码库 v2 能力 |
| GET | `/api/state` | 当前状态快照(§3.3) |
| GET | `/api/codes` | 码库数组 |
| GET | `/api/events` | **SSE**:`hello` / `state` / `codes` / `event` / `log` |
| POST | `/api/cmd` | body `{"cmd":"SEND 1"}` 或纯文本;202 入队 |
| POST | `/api/ota` | 原始 `.bin`,`Content-Length` + 头 `X-RFLAB-OTA`;200 后重启;见 §3.4 |
| POST | `/api/wifi` | `{"ssid":"...","pass":"..."}`;存 NVS 并尝试连接(AP 保持);202 |
| POST | `/api/wifi/clear` | 删除 STA 凭据,回 AP-only;202 |
| GET | `/api/net` | AP/STA 详情与 RSSI |

约定:

- JSON 一律 UTF-8、无 BOM;未知字段忽略。
- `POST` 只表示**入队成功**,执行结果通过 SSE `event`/`log` 返回。命令最长 96 字节,队列深度 8;满时 503。
- SSE 每 10s 发 `: ping`;客户端断开由发送失败检测。
- 响应头:`Cache-Control: no-store`;API 带 `Access-Control-Allow-Origin: *`(仅本地开发便利,不构成鉴权)。
- `GET /api/events` 首帧发 `hello`,随后在快照序号变化时推送 `state`/`codes`。

### 3.3 状态快照

```json
{
  "fw": "0.7.1", "proto": 1, "uptime_ms": 123456,
  "net": {"mode":"apsta","ap_on":1,"has_creds":1,
          "ap_ssid":"RF-Lab-AB12","ap_ip":"192.168.4.1",
          "sta_connected":true,"sta_ssid":"home","sta_ip":"192.168.1.50","rssi":-57},
  "ble": {"on":1,"conn":0,"name":"RF-Lab-AB12","pin_set":1},
  "module": {"baud":9600,"rx_bytes":296,"frames":37,"acks":0,"dups":3,
             "stray":0,"resync":0},
  "store": {"count":5,"max":32,"ver":2},
  "oled": {"present":1,"on":1,"flush":43,"err":0,"max_us":8747},
  "ota": {"armed":0,"pct":0,"phase":"idle","slot":0,"next":1,"pending":0},
  "tx": {"active":0,"kind":"idle","id":0,"ok":0,"ms":0},
  "last": {"kind":"rx","id":2,"band":"315M","code":"5555033C","ms":123}
}
```

码库数组元素(空字段省略;`manual/edited` 只在为 1 时出现):

```json
{"id":1,"band":"315M","code":"5555034C","name":"客厅大门","group":"家门","sym":"🚪","manual":0,"edited":0}
```

`name` 最长 24B UTF-8,`group` 16B,`sym` 8B;`manual`=手工建码,`edited`=建码后改过 band/code。

事件对象(SSE `data`,或 BLE 一行):

```json
{"t":"event","seq":8,"kind":"learn","id":6,"band":"315M","code":"5555034C","line":"LEARN id=6 ..."}
{"t":"event","seq":9,"kind":"tx","tx":"send","id":1,"band":"315M","code":"...","ok":1,"ms":852,"line":"OK tx ..."}
{"t":"log","seq":10,"line":"OK mode=continuous"}
{"t":"state","seq":11,"data":{...}}
{"t":"codes","seq":4,"items":[...]}
{"t":"hello","fw":"0.7.1","build":"a7b4bf3","ui":"85a1a9b4","proto":1,"codebook":2,"name":"RF-Lab-AB12","auth":1}
{"t":"auth","ok":1}
```

`tx.kind`:`send|long|stop`;`tx.active=1` 表示长发进行中。`seq` 单调递增,溢出回绕不算错误。

**下行信封是兼容契约(2026-11-22)**:

- `state`/`codes`/`event`/`log` 的字段**只增不减**;客户端必须忽略未知字段。
- `{"t":"codes","seq":N,"items":[...]}` 的 `items` 必须是**完整 JSON 数组**,
  信封必须带结尾 `}`;少一个括号客户端会整块解析失败(2026-11-22 APP 码库空白即此因)。
- 容量(`store.max`)是**数据**,不是 schema;固件从 32 提到 64 不应要求 APP 同步升级。
- 信封由固件 `link_codes_header()` / `link_codes_wrap()` 统一生成,并进主机测试;
  BLE/SSE 不允许各自手写字符串。
- 固件/APP 任一侧升级时,旧 APP 必须至少能继续显示码库(`items`)与状态;
  破坏性改动要同步 bump `hello.proto` 并先在 `01-ui.md` 记录。

### 3.4 固件升级(OTA)

两个目标分开:**设备固件走 OTA;Android APK 走 APP 自更新(§3.5),两者互不覆盖**。
APK 里的页面是构建时冻结的副本;设备端页面与固件一起更新,所以网页端会跟随固件。

| 项 | 规范 | 唯一来源 |
|---|---|---|
| 分区 | `nvs` 0x9000/0x6000 · `phy` 0xf000/0x1000 · `otadata` 0x10000/0x2000 · `ota_0` 0x20000/0x1F0000 · `ota_1` 0x210000/0x1F0000;无 factory | `firmware/partitions.csv` |
| 首次迁移 | 旧单 app 表不能在运行时替换,**必须 USB 跑 `./tools/flash.sh`**;之后才能 OTA | `tools/flash.sh` |
| 触发 | 串口 `OTA` 生成 token;`OTA OFF` 取消;HTTP/BLE 调用一律 `ERR OTA is serial-only` | `firmware/src/main.c` |
| token | 8 位大写十六进制;10 分钟;错误 5 次锁定;OLED 顶部显示 10s;上传中断不消耗 | `firmware/src/ota_ticket.c` |
| 上传 | `POST /api/ota`;头 `X-RFLAB-OTA`;`Content-Length` + 原始 `.bin`(非 multipart);4KB 分块写非运行槽 | `firmware/src/web_server.c` |
| 结果 | 200 `{ok,bytes,slot,reboot}` 后约 1.5s 重启;401 token;409 未 armed/忙;400 镜像无效/中断 | 同上 |
| 回滚 | 新镜像首次启动 `PENDING_VERIFY`;`main.c` 6s 后 `mark valid`,之前崩溃/复位由引导器回滚 | `firmware/src/ota.c` |
| 进度 | `/api/state.ota` 的 `armed/pct/phase/slot/next/pending`;SSE `state` 推送 | §3.3 |
| Web UI | 帮助面板 `U` / `FIRMWARE UPDATE`:镜像 + token + 上传进度;BLE/APP 显示“不支持”,不隐藏 | `web/index.html` |
| 一键更新(0.7.3 规划) | 浏览器查 Pages manifest → BOOT 物理确认 → 下载/上传;设备校验 SHA-256;APP/BLE 不支持 | §3.4.1(规划) |
| 工具 | `python3 tools/ota.py --host <ip> --serial /dev/ttyACM0`(或 `--token`) | `tools/ota.py` |

> 0.7.3 规划新增「物理确认后 HTTP arm」的例外(§3.4.1);在 0.7.3 之前,触发仍只认串口 `OTA`。

**安全边界(写死)**:HTTP 无登录,所以端点默认关闭;token 只挡“同网随手刷机”,
不挡有备而来的攻击者,也不是签名。**不做 secure boot / 签名校验**;能拿到 token 的人
就能刷任意固件。AP 密码/局域网可达性仍是第一道门。

**不做的更新路径**:BLE/APP 上传固件(1MB 走 BLE 太慢且要重做分片/校验)、云推送、
UI 单独打包(LittleFS)。

验收:见 §8 `UI-19`。

#### 3.4.1 UI 一键更新(0.7.3 规划,未实现)

**目标**:在设备页 `FIRMWARE UPDATE` 面板里完成「检查最新版 → 下载 → 校验 → 写入非运行槽 →
重启 → 显示新 `build`」;用户不再自己找 `.bin`、抄 8 位 token。手动「镜像 + token」上传保留为
离线/救援路径,不删除。

**范围(写死)**:

- 只做 **Web UI**(浏览器打开设备 LAN IP / AP IP);**Android APP 仍是 BLE-only**,不新增 BLE OTA,
  面板显示「固件更新请用浏览器」;uConsole TUI 不加更新入口。
- 仍然**不做**:固件签名/secure boot、云推送、静默安装、APK 更新。APK 走 §3.5 的独立自更新。
- 仍然要求**物理确认**才能 arm;HTTP/BLE 不能单独把设备置于可刷写状态。

**已拍板(2026-11-22)**:物理确认 = **BOOT**;固件源 = **GitHub Pages**;0.7.3 **独立发版**。
执行计划见 [`02-plan.md`](02-plan.md) §5.2。

**为什么是「浏览器拉 Pages,再上传给设备」**:

| 方案 | 结论 | 原因 |
|---|---|---|
| 设备自己拉 GitHub Release | ❌ 首版不做 | 需要 TLS + SNTP 校时 + CA bundle + 重定向;C3 的 RAM/Flash 与 GitHub 可达性都是新风险;AP 模式仍无外网 |
| 浏览器直接拉 GitHub Release 资产 | ❌ 不可行 | 2026-11-22 实测 Release 资产**没有** `Access-Control-Allow-Origin`;跨域 `fetch` 会被浏览器拦截 |
| **浏览器拉 GitHub Pages 上的固件** | ✅ **推荐** | Pages 的 HTML/JS 返回 `access-control-allow-origin: *`(同日实测);`/firmware/*.bin` 在 M3 用实际文件复验;设备只收普通 HTTP 上传,不需要 TLS 客户端 |
| 手动 `.bin` + token | ✅ 保留 | 离线/救援/CI 回归都还要用 |

CORS 实测记录:[`evidence/2026-11-22-pages-cors.log`](evidence/2026-11-22-pages-cors.log)。

**用户流程**:

1. 打开 `U / FIRMWARE UPDATE`;面板显示当前 `fw` / `build` / `ui` / `slot` / `pending`;
   **不自动联网**。
2. 点 `CHECK LATEST`;浏览器 `fetch(<firmware-base>/manifest.json?t=<epoch>, {cache:"no-store"})`,
   8s 超时;失败时显示「无网络 / Pages 不可达」并保留手动上传。`?t=` 用来绕过 Pages/CDN 的
   10 分钟缓存,避免发版后仍读到旧 manifest。
3. 校验 manifest;比较版本;显示最新版、大小、SHA-256 前 12 位、变更说明。
4. 点 `UPDATE`;二次确认后 `POST /api/ota/arm`;OLED 显示 `OTA WAIT / HOLD BOOT`;
   用户按住板载 **BOOT(GPIO9)2s**;设备 arm,UI 轮询 `GET /api/ota/arm/status` 取 token。
5. 浏览器下载 `firmware.bin`(显示下载进度),再 `POST /api/ota` 上传,
   头带 `X-RFLAB-OTA` 与 `X-RFLAB-SHA256`;设备边写边算 SHA-256,不匹配立即 `ota_abort`。
6. 设备重启;UI 轮询 `/api/hello`,比较 `build`(不只 `fw`);成功后显示新版本并提示刷新。
   若 `hello.ui` 与当前页面 `UI_HASH` 不同,提示「页面已随固件更新,请刷新」;
   **APP 页面是 APK 构建时冻结的副本,仍需走 §3.5 的 APP 自更新**,一键固件更新不会更新 APK。
   NVS(码库/Wi-Fi/BLE PIN)不动;失败/断电时仍从旧槽启动(现有双槽回滚)。
7. Fallback:手动选 `.bin` + 串口 `OTA` token,流程与 0.7.1 相同。

**Manifest 契约**(Pages 上的 `firmware/manifest.json`):

```json
{
  "schema": 1,
  "version": "0.7.3",
  "build": "a1b2c3d",
  "ui": "deadbeef",
  "file": "rf-lab-firmware.bin",
  "size": 1098608,
  "sha256": "64 位小写 hex",
  "min_from": "0.7.0",
  "released_at": "2026-11-22T00:00:00Z",
  "notes": "短说明;详情指向 Release"
}
```

规则:

- `schema` 必须为 1;`version` 数字段比较,不认 `v` 前缀/预发布;`file` 只允许同目录 basename,
  拒绝 `../`、绝对 URL、查询串;`size` 必须 ≤ 1,900,000 B(1.94MB 槽留余量);
  `sha256` 必须 64 位 hex;`min_from` 缺省视为不限制。
- 当前 `fw < min_from` → 拒绝并提示「旧分区表需 USB `./tools/flash.sh` 一次」;
  当前 `fw == version` → 显示「已是最新」;当前 `fw > version` → 显示「当前高于线上稳定版」;
  两种情况都不提供降级/同版重装(避免误刷)。
- URL 固定为 `https://heiheiheiheiheihei.github.io/rf-lab/firmware/`;换域名/换 Pages 时必须重新验证 CORS。
  0.7.3 的 UI 里把 base URL 写成常量,不跟设备 IP 拼。
- base URL 由 `web/index.html` 的 `<meta name="rflab-ota-base" content="...">` 提供,
  默认是上面的 Pages 目录;自托管/换域名只改这一处,再由 `tools/build_web.py` 重新生成。
  设备页只接受 `https://` 的 base,拒绝 `http://`/相对路径,避免降级到明文。

**Arm 契约(新增)**:

| 端点 | 作用 | 成功返回 |
|---|---|---|
| `POST /api/ota/arm` | 请求进入「等待物理确认」,不返回 token;body 可带 `{size,sha256,version}` | `202 {"ok":true,"state":"wait_button","ttl":30}` |
| `GET /api/ota/arm/status` | UI 轮询;仅同一客户端 IPv4 可见 token | `{"state":"wait_button|armed|expired","ttl":…,"token":"8HEX"?}` |
| `POST /api/ota/arm/cancel` | 取消等待/清除 token | `200 {"ok":true}` |
| `POST /api/ota` | 既有上传;新增可选 `X-RFLAB-SHA256` | `200 {ok,bytes,slot,reboot}` |

设备侧规则:

- **BOOT=GPIO9**,按住 2s 才 arm;启动后前 5s 不响应(避免 strapping/下载模式误触);
  30s 未按 → `expired`;`OTA OFF`/上传完成/超时都取消等待。
- token 仍是 8 位十六进制、10 分钟、一次性;新增**绑定 arm 请求的客户端 IPv4**,
  换 IP 上传返回 401。token 不出现在 `/api/state`/SSE/串口日志,只在 OLED 与
  **同 IP** 的 `arm/status` 响应里。
- `POST /api/cmd {"cmd":"OTA"}` 仍返回 `ERR OTA is serial-only`;BLE 没有 arm 端点。
- arm 请求限速 3 次/分钟;已有 token 未过期时重复 arm 返回 409,不刷新 token。
- arm 可带 `size/sha256/version`,设备存进本次 token;**上传的 `Content-Length` 与
  `X-RFLAB-SHA256` 必须与之一致**,不一致 400,不写/回滚。
- **已拍板(2026-11-22):物理确认 = BOOT(GPIO9)按住 2s。** 0.7.3 不以 OLED code
  作为备选;若 1.0 外壳挡住 BOOT,再单独立项硬件方案(开孔/独立按键),不在本版中途切换。

**上传/校验规则**:

- `Content-Length` 必须等于 manifest `size`(或 arm 记录的 size);超过槽余量在 `ota_begin` 前
  拒绝(409),不写 flash。
- `X-RFLAB-SHA256` 若存在必须是 64 位 hex;格式错 400,不开始写;与 arm 记录不一致 400。
- 设备在 `ota_write` 流里累计 SHA-256;`ota_finish` 与 `X-RFLAB-SHA256` 比较,不一致 →
  `ota_abort` + 400,旧槽不变。**设备侧哈希是权威**,不依赖浏览器 `crypto.subtle`:
  设备页是 `http://192.168.x.x`,不是 secure context,WebCrypto 不可用。
- 设备仍用 `esp_ota_end` 做镜像有效性校验;`PENDING_VERIFY`/6s 回滚逻辑不变。
- 上传中断/超时/断电:旧槽继续启动;UI 显示「设备未重启/仍在旧镜像」,可重试。

**安全边界(写死)**:

- 一键更新**没有降低** arm 门槛:必须有物理确认(BOOT;或后续 OLED code),token 绑定 IP,
  一次性、10 分钟。
- SHA-256 只证明「下载的字节 = manifest 声明的字节」,**不是签名**;Pages/仓库被篡改时仍可能
  下发恶意固件。没有 secure boot。要更强保证,另案做 detached signature(1.0 之前不承诺)。
- HTTP 仍无登录;AP 密码/局域网可达性仍是第一道门。**不要把一键更新写成「安全启动/加密」**。
- 默认页面仍零外部请求;只有用户点 `CHECK LATEST` 才访问 Pages。官网 iframe demo 必须拦截
  `manifest.json` 并标 `SIM`,不能真联网。

### 3.5 Android APP 自更新(0.7.0 起)

**结论**:APP 不在“设备 OTA”链路里;它是自己的客户端,查公开的 GitHub Release,
下载后校验、交给系统安装器。固件和 APK 仍是**两条独立更新链路**;0.7.1 起允许同号发布
(本次固件 0.7.1 / APK 0.7.1),但 **APP 更新永远不会更新设备固件**。

| 项 | 规范 | 唯一来源 |
|---|---|---|
| 检查 | 冷启动/回前台,6 小时节流;`GET api.github.com/repos/<repo>/releases?per_page=30` | `android/.../MainActivity.java` |
| 选版本 | 跳过 draft/prerelease;只认带 `rf-lab-android.apk` 资产的 Release,取最高版本 | `android/.../Updater.java` |
| 比较 | tag 去 `v` → `versionName`;数字段比较,`0.7.0 > 0.7.0-rc1`,`0.10.0 > 0.9.0` | `android/.../AppVersion.java` |
| 提示 | 弹窗:体积 + Release 说明 + **一键更新 / 忽略此版本 / 稍后** | `MainActivity.java` |
| 忽略 | 记该版本号(SharedPreferences,key 在 `rflab_update`);同版本不再提示,下一版重新提示 | 同上 |
| 下载 | 仅 HTTPS、上限 40MB、写 `cache/update/`,进度百分比 | `Updater.java` |
| 校验 | Release 的 `SHA256SUMS.txt`(按 basename 匹配)→ 包名 + `versionCode`/`versionName` 必须前进 → 签名证书与已装 APP 一致 | 同上 |
| 安装 | `PackageInstaller` 会话 + 系统确认框;未允许「安装未知应用」时先跳设置,回来自动续下 | `Updater.java` / `MainActivity.java` |
| 权限 | `INTERNET`、`REQUEST_INSTALL_PACKAGES` | `AndroidManifest.xml` |
| 主机测试 | `./tools/app_update_test.sh`(版本比较 + SUMS 查表,36 checks) | `tools/app_update_test.sh` |

**边界(写死)**:

- **不是静默更新**:系统确认框必须用户点;不申请无障碍、不 root、不需要 ADB。
- **不是云推送**:APP 主动拉公开 Release,仓库不跑推送服务。
- **失败关闭**:缺 `SHA256SUMS.txt` 条目、大小不符、版本没前进、签名证书不同,任一命中就不安装。
- **不是签名校验的替代**:设备 OTA 仍无签名/secure boot(§3.4);Android 端靠包签名与系统校验。
- **忽略不跨版本**:只对当前版本号生效。
- **真机已验(2026-11-22)**:0.7.0→0.7.1 弹窗/下载/系统安装器/覆盖安装成功;
  证据 [`2026-11-22-app-ble.md`](evidence/2026-11-22-app-ble.md)。

验收:见 §8 `UI-20`。

## 4. BLE 协议

| 项 | 值 |
|---|---|
| 设备名 | `RF-Lab-XXXX` |
| Service | `5a3d0001-7c1f-4b8e-9a55-52464c414231` |
| RX(客户端写) | `5a3d0002-7c1f-4b8e-9a55-52464c414231` |
| TX(设备通知) | `5a3d0003-7c1f-4b8e-9a55-52464c414231` |
| 属性 | RX:WRITE / WRITE_NO_RSP;TX:NOTIFY |
| MTU | 首选 247;通知按 `MTU-3` 分片 |
| 编码 | UTF-8 行协议;`\n` 结束;客户端按 `\n` 重组 |
| 广播 | 连接模式 UND;广播名 + 128-bit Service UUID 在 scan response |

命令与 HTTP 相同,一行一条。鉴权:

1. 连接后设备发 `{"t":"hello",...,"auth":0}`。
2. 客户端发 `AUTH <4位PIN>`;成功 `{"t":"auth","ok":1}`,之后所有命令可用。
3. 未鉴权只接受 `AUTH`;连续 5 次错误断开并暂停广播 10s(实现为断开后由 `start_adv` 重新广播;暂停窗口未单独做)。
4. PIN 存 NVS(`ble_pin`),首次启动随机 4 位;OLED 开机页显示 5s;串口 `PIN` 可查。

PIN 是**应用层**,不改变 BLE 链路加密状态;抓包者仍能看到明文。它挡的是"隔壁随手连上就发码",不是有备而来的攻击者。

3. **代码一致**:`firmware/src/main.c` 只 `#include "wiring_config.h"`,不再重复定义
   `PIN_*` / `CONSOLE_BAUD` / `MODULE_BAUD_DEFAULT` / `OLED_I2C_HZ`;`MODULE_UART` 固定
   `UART_NUM_1`。如果 JSON 与代码不一致,固件构建直接失败。
4. **不越权**:只画现役 CORE-C3 + YS-RF34DL;CC1101 / NRF24L01 / SI4463 / LR1121
   仍是路线图,不进入“现役链路”图/表。
5. **不新增数据路径**:`HW` 模态只展示静态 SVG,不 `fetch`、不新增 API/命令/事件;
   `SEND/LONG/STOP`、ARM 语义、元素 ID 不变。
6. **体积**:Web 首屏 gzip < 80KB;固件 app < 1.94MB 槽;不引外部字体/图片/CDN。

验收:见 §8 `UI-18`。

## 9. 关键判断与避免的误修

1. **为什么所有传输只提交既有命令行,而不是各写一套 API?**
   0.5.0 的命令语义(尤其 `F0` 0.85s、`FE/FF`)已被上机验证;复制业务逻辑等于复制 bug。新增层只做"传输 → 一行命令 → 事件"。

2. **为什么 Web 用 SSE 而不是 WebSocket?**
   事件是单向、低频;SSE 是普通 HTTP,ESP-IDF 的 `httpd_resp_send_chunk` 足够,浏览器自动重连,Android WebView 也原生支持。省掉 WS 握手/掩码/分片代码与 RAM。

3. **为什么不把 UI 放 LittleFS?**
   单页 gzip 约 30KB,直接 `EMBED_FILES` 进 app 分区:少一个分区、少一种掉电损坏面、烧录即整体一致。代价是改 UI 仍要重建/烧录一次;0.6.0+ 的双槽 OTA 更新整包(含页面),之后不再需要拆机。

4. **为什么 BLE 用 NimBLE 而不是 Bluedroid?**
   C3 只有 400KB SRAM,同时要 Wi-Fi + HTTP + 事件环。NimBLE 的 RAM/Flash 占用显著更小;代价是 API 更底层,需要自己写 GATT 表。

5. **为什么状态快照按序号推送,不把每次 ACK 都推?**
   长发心跳 ~25Hz;每次推 JSON 会把 BLE 带宽和手机电量吃光。代码只推**变化后的快照**(上限 5Hz),心跳只进计数器。

6. **为什么 ARM 默认关?**
   手机放在口袋里误触 `SEND` 会真的发码。ARM 是本地 UI 状态,不假装是安全机制;串口行为保持 0.5.0 不变。

7. **避免的误修**:
   - ❌ 把 Wi-Fi 凭据写死在源码:换网络要重编。→ NVS + Web 配网。
   - ❌ STA 连不上就关 AP:用户失去入口。→ 15s 失败后打开 AP 回退。
   - ❌ AP 里配网成功立刻关 AP:会踢掉正在配网的浏览器。→ 配网成功后保持 AP,下次启动再 STA-only。
   - ❌ BLE 用明文无 PIN:隔壁随手可发。→ 应用层 PIN + 失败退避。
   - ❌ 为省事把 OLED 状态页换成网络日志:72×40 放不下,且会破坏已验证的 0.5.0 页。→ 只加一行网络状态/开机 PIN 页。
   - ❌ 用 `deep sleep` 省电:会断 Wi-Fi/BLE,也丢模块 UART。→ 不做。

8. **为什么统一视觉,却不复用官网的 CSS/JS?**
   官网是 41KB HTML + 62KB CSS + 30KB JS 的滚动宣传页,带 Canvas 频谱、滚动揭示和配装器;
   固件单页受 1.94MB OTA 槽、80KB 级 gzip 预算与**首屏无外部请求**约束
   (0.7.3 的 `CHECK LATEST` 是用户点击后的唯一例外,见 §3.4.1)。复用代码会把官网的
   交互与体积带进设备。**统一 token 与组件语法,不统一代码**:`site/style.css :root` 是色板/字体的
   唯一来源,`web/app.css` 复制值而不 `@import`;改版式各改各的,只有设备 UI 变化才重拍官网截图。

9. **避免的误修(视觉统一)**:
   - ❌ 为“看起来一样”把 `site/` 的 Canvas/滚动动画塞进 `web/`:挤占固件空间,且平板上无法滚动。
   - ❌ 把终端改成官网式长页面/导航:现场终端是一屏操作,滚动会遮住码库与 STOP。
   - ❌ 只改颜色不改组件语法(圆角/切角/角标/等宽标签):截图仍会像两套产品。

10. **为什么 OTA 用双槽 + 串口 token,而不是把页面放 LittleFS / 常开 HTTP 上传?**
    UI 只有 ~25KB gzip,单独做 LittleFS 会多一个可损坏文件系统与两套资源源;整包双槽让
    “页面和固件永远同版本”,回滚也只回滚整个镜像。HTTP 无登录,端点常开等于同网任何人可刷机;
    token 把窗口缩到“人在串口前 10 分钟”,但**仍不是签名**。代价:首次迁移必须 USB,
    app 槽从 2MB 单槽变成 1.94MB 双槽,且 APP 的页面仍需重打 APK。
