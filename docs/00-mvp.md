# RF-Lab MVP — 315/433 固定码 学习 / 复制 / 发射

状态:现行 · 2026-11-15 · 固件 **0.4.0** · **本文件是唯一规格**

## 1. 目标

一台 315/433MHz 固定码遥控器的「学码 → 存 → 发射」工具:

> 按一下原遥控器 → 模块解码 → ESP32 存码 → 串口命令发射 → 原接收器动作。

两块板:**ESP32-C3 OLED** 只做「串口 ↔ 命令行」;**YS-RF34DL** 负责解码、编码、发射。

## 2. 硬件方案(已定稿,只剩两块板)

| 方案 | 结论 | 理由 / 代价 |
|---|---|---|
| ESP32-S3 + AS10/AS07/AS01 三模块(SPI + 三路 LDO + AND 门控) | ❌ 放弃 | 寄存器驱动 + 供电门控,多轮探测未通过;频段覆盖是需求膨胀 |
| ESP32-S3 + 双频模块 + 独立 OLED + 3 按键 + 电源开关 | ❌ 放弃 | 面板/按键不是核心;每件都是一处排线与装配故障点 |
| **ESP32-C3 OLED + YS-RF34DL** | ✅ 采用 | 固定码学习/存/发全在模块内;ESP32 只做串口桥,接线 4 根 |

| 件 | 型号 / 规格 | 接口 |
|---|---|---|
| 主控 | ESP32-C3 0.42" OLED 板(SSD1306 72×40,**SDA=GPIO5 / SCL=GPIO6**,0x3C;原生 USB;4MB Flash) | USB-C |
| 射频 | YS-RF34DL 315/433 编解码模块(STC15 主控,3.2×2.5×1.2cm) | TTL 串口 9600 8N1 |

**代价(写死,不要在执行时忘掉)**:

- **没有本地显示与按键**:不接主机(手机/电脑 USB)就看不到状态,所有操作走串口。板载 OLED 本版**不驱动**,但 5/6 按已占用处理。
- **只做固定码**(EV1527 / PT2262/2260/2240 族):滚动码学不会,也测不了,不能据此断言滚动码设备安全。
- **没有发射硬门控**:模块常带电,固件每发出一条帧就是真的在发。旧方案的 `RF_KILL` 物理开关随三模块方案一起消失 —— 这是主动丢掉的一条安全能力。
- **模块行为不完全公开**:发射时长单位、应答时机、学习码写入方式均无文档,只能实测标定。

## 3. 接线

**唯一权威是 [`hardware/README.md`](../hardware/README.md)**,这里只留结论:

| 模块脚 | 接到 ESP32-C3 | 说明 |
|---|---|---|
| VCC | `3V3` | 见 §4,不要接 5V |
| GND | `GND` | 必须共地 |
| TXD | `GPIO4`(UART1 RX) | 模块发 → ESP32 收 |
| RXD | `GPIO3`(UART1 TX) | ESP32 发 → 模块收 |

**为什么不是 GPIO5/6**:那是板载 OLED 的 I2C 引脚;这两根线焊死在板上,不能挪作模块串口。

天线:17–23cm 单芯(可卷),尽量竖直、远离金属与手;不接天线时距离只有 1–5m。

## 4. 供电与电平 —— ★ 本文档最大的未定项

模块说明书自相矛盾:

| 出处 | 写的 |
|---|---|
| 核心参数 | 工作电压 DC **3.3–5V(宽电压)** |
| 引脚定义 | VCC **4.5–5.5V** |
| 应用举例 | 接单片机「**需要外加 3.3V 转 5V**」 |

**决策:按 3.3V 直连**(VCC 与 TTL 同电压)。

**理由**:VCC 与逻辑电平必须一致。若 5V 供电,模块 TXD 输出 5V,而 ESP32-C3 的 GPIO 绝对最大只有 3.6V(**会打坏**);同时 ESP32 的 3.3V TX 低于 5V TTL 的 VIH(≈0.7×VCC = 3.5V),模块收不到可靠高电平。3.3V 下两侧天然匹配,零额外器件。

**代价 / 风险**:

- 3.3V 落在「核心参数」内,但低于「引脚定义」的 4.5V,**发射功率与距离没有保证**;模块内部升压到 10V 是否够劲,只能实测。
- 2026-11-15 已按 **3V3 直连**上机:收发、改波特率、应答全部正常,学习型遥控器也学到了发射码(见 §11)—— 「3.3V 能工作」已被证实;**距离**仍未测。

**升级路径(仅当实测距离不够)**:改 5V 供电 + `TXD` 串 1kΩ/2kΩ 分压到 GPIO4 + ESP32 的 `GPIO3` 经 5V 缓冲(74HCT1G125 或 BSS138 电平转换)→ 模块 RXD,共地。这是**改接线,不是换方案**。

**禁止**:5V 直接接 GPIO4/GPIO3;上电前必须量模块 TXD 空闲电压(应 ≈3.3V)。

## 5. 模块串口协议(已被实测确认)

帧长固定 **8 字节**,`FD` 开头、`DF` 结尾;第三个字节在两个方向含义不同。

### 5.1 发射

| 用途 | 帧 |
|---|---|
| 315M 发射 | `FD F3 03 c0 c1 c2 c3 DF` |
| 433M 发射 | `FD F4 03 c0 c1 c2 c3 DF` |
| 315M 长发 | `FD F3 FE c0 c1 c2 c3 DF` |
| 315M 停止 | `FD F3 FF c0 c1 c2 c3 DF` |

第三字节 `03` 是「发射持续时间」(单位未给);`FE` 长发、`FF` 停止。

### 5.2 解码输出

| 频段 | 帧 |
|---|---|
| 315M | `FD F3 03 c0 c1 c2 c3 DF` |
| 433M | `FD F4 03 c0 c1 c2 c3 DF` |

第三字节固定 `03`;`c0..c3` 是解码得到的 4 字节「遥控器信息」,**原样存、原样回放**,固件不解析 EV1527 的地址/按键位。

### 5.3 配置与应答(延迟为 2026-11-15 实测)

| 命令 | 帧 | 应答 | 应答延迟 |
|---|---|---|---|
| 设 4800 | `FD 01 F1 00 00 00 00 DF` | `F1` | — |
| 设 9600 | `FD 02 F1 00 00 00 00 DF` | `F1` | ~0.15s |
| 设 57600 | `FD 03 F1 ... DF` | `F1` | ~0.10s |
| 设 115200 | `FD 04 F1 ... DF` | `F1` | — |
| 单次输出 | `FD 01 F2 ... DF` | `F2` | ~0.05–0.15s |
| 连续输出 | `FD 02 F2 ... DF` | `F3` | ~0.05–0.15s |
| 单帧发射(dur=03) | `FD F3 03 … DF` | `F0` | **~0.85s** |
| 长发(dur=FE)/ 停止(dur=FF) | `FD F3 FE/FF … DF` | **无** | 未收到 F0 |

**要点**:`F0` 明显晚于 `F1/F2/F3`(0.85s vs 0.1s),等待窗口必须 ≥1s,否则会把成功报成失败。长发/停止不回 F0 —— 是模块行为,不是固件漏读(用 `MON` 逐字节看过,确实没有)。

### 5.4 实测证据(2026-11-14,真模块)

9600 8N1,最短脉宽 104µs;按遥控器收到(16 字节 = 同一帧连发两次):

```
FD F3 03 55 55 03 3C DF  FD F3 03 55 55 03 4B DF
```

即:**315M**,两个按键的码分别是 `5555033C` / `5555034B`(低字节不同)。这条抓包是「文档帧格式 = 模块实际输出」的现场证据。

### 5.5 说明书里已知的矛盾(以实测为准)

| # | 矛盾 | 处理 |
|---|---|---|
| 1 | 供电 3.3–5V vs 4.5–5.5V | 按 3.3V 接,见 §4 |
| 2 | FAQ 说「F0 F0 … 共 8 字节」 | 实测是 `FD … DF`,以实测为准 |
| 3 | FAQ 的命令写成 `0x0F, 0x01, 0xF2…` | 疑 OCR 错误,实际是 `0xFD` |
| 4 | 「03 代表发射持续时间」无单位 | 默认用 03;长发/停止用 FE/FF |
| 5 | 学习码存 20 个,但没给写入触发方式 | 本版**不使用**模块侧学习存储,只用解码输出 |
| 6 | 应答是单字节还是帧、在哪个波特率发出 | **已实测**:单字节;`F1/F2/F3` 约 0.1s,`F0` 约 0.85s;改波特率时 `F1` 落在旧波特率上 |

## 6. 固件行为

| 命令 | 作用 | 正常返回 |
|---|---|---|
| `HELP` | 命令表 | — |
| `INFO` | 固件/模块波特率/计数(stray、resync 是「可见失败」的度量) | `OK stored=…` |
| `LIST` | 列出已存码 | ` 1  315M 5555033C` |
| `SEND <id>` | 发射一次(dur=03) | `OK tx id=1 band=315M code=…` |
| `LONG <id>` | 长发(dur=FE) | 无应答(实测);固件打印 `WARN … no F0` |
| `STOP <id>` | 停止发射(dur=FF) | 无应答(实测);固件打印 `WARN … no F0` |
| `ERASE <id|all>` | 删除 | `OK erased …` |
| `MODE single\|continuous` | 模块解码输出模式 | `OK mode=…` |
| `BAUD <n>` | 改模块波特率(4800/9600/57600/115200) | `OK baud=…` |
| `RECOVER` | 扫模块波特率并强制回 9600 | `OK module baud=9600` |
| `RAW <hex>` | 向模块注入任意字节(调试) | `OK raw n B` |
| `MON ON\|OFF` | 逐字节 hex 打印模块数据(调试) | — |
| `ECHO ON\|OFF` | 是否打印解码事件 | — |
| `RESET` | 重启 ESP32 | — |

规则:

- **学码是自动的**:模块一直处于接收态,按遥控器即输出帧;固件把新码入库(NVS,最多 32 条)并打印 `LEARN id=N …`。同码 600ms 内只算一次(实测一次按键会连出多帧)。
- **启动时不给模块发任何配置命令**:模块行为未公开,少发一条就少一个假证据源;`MODE`/`BAUD` 只在用户显式要求时发。
- **等应答**:发射后等 `F0` 最多 1500ms(实测 0.85s),收到打印 `OK …`,没收到打印 `WARN … no F0`(不静默)。长发/停止本来就不回应答,所以它们总是打印 `WARN` —— 这是模块行为,不是失败。
- **发射优先**:模块自身规定解码期间收到发射命令优先发射,固件按顺序写,不做额外调度。

## 11. 上机记录(2026-11-15)

ESP32-C3 0.42" OLED + YS-RF34DL,VCC **3V3 直连**,模块 TXD→GPIO4 / RXD→GPIO3,主机 Linux 经原生 USB CDC。
逐条命令、时间戳与原始观察见 [`evidence/2026-11-15-bringup.md`](evidence/2026-11-15-bringup.md)。

| 结论 | 依据 |
|---|---|
| 学码 3 个键:`5555034C` / `5555033C` / `5555034B`,均 315M | 按原遥控器时的 `LEARN id=1..3` |
| 发射 15/15 成功 | 每次 `SEND` 都在 ~0.85s 收到 `F0` |
| **空中链路成立**(不只是 UART ACK) | 学习型遥控器学到 `5555034B`,再按它时模块解回同一个码 |
| 波特率可改 | `BAUD 57600` → `SEND` → `BAUD 9600`,两段都收到 `F1` |
| 长发/停止不回 `F0` | `MON` 逐字节确认只有发送帧、没有回包 |
| 一次异常:教学期间 `stray` 累积 72 字节 | 之后 5 次正常按键 `stray` 不变、帧全长 8 字节干净;未复现 |
