# RF-Lab MVP — 315/433 固定码 学习 / 复制 / 发射

状态:现行 · 2026-11-21 · 固件 **0.7.1** · **本文件是射频/命令的唯一规格**

> 跨平台 UI(Web / BLE / Android / uConsole)的规格单独放在 [`01-ui.md`](01-ui.md);
> 本文只保留硬件、模块协议、命令语义与射频验收。两者冲突时,射频行为以本文为准,
> UI 传输细节以 `01-ui.md` 为准。

## 1. 目标

一台 315/433MHz 固定码遥控器的「学码 → 存 → 发射」工具:

> 按一下原遥控器 → 模块解码 → ESP32 存码 → **OLED 显示状态** → 串口/Web/BLE/uConsole 发射 → 原接收器动作。

两块板:**ESP32-C3 OLED** 做「串口/Wi-Fi/BLE ↔ 命令行」,并用板载 72×40 OLED 做本地状态显示;
**YS-RF34DL** 负责解码、编码、发射。

0.6.0 起 C3 的 **Wi-Fi(STA 优先 / AP 回退)+ BLE** 只承载控制 UI(Web/Android/uConsole),
315/433 的调制、解码、发射仍全部在 YS-RF34DL 内;C3 的 2.4G 射频不参与射频链路。

## 2. 硬件方案(已定稿,只剩两块板)

| 方案 | 结论 | 理由 / 代价 |
|---|---|---|
| ESP32-S3 + AS10/AS07/AS01 三模块(SPI + 三路 LDO + AND 门控) | ❌ 放弃 | 寄存器驱动 + 供电门控,多轮探测未通过;频段覆盖是需求膨胀 |
| ESP32-S3 + 双频模块 + 独立 OLED + 3 按键 + 电源开关 | ❌ 放弃 | 面板/按键不是核心;每件都是一处排线与装配故障点 |
| **ESP32-C3 OLED + YS-RF34DL** | ✅ 采用 | 固定码学习/存/发全在模块内;ESP32 只做串口桥,接线 4 根 |

| 件 | 型号 / 规格 | 接口 |
|---|---|---|
| 主控 | ESP32-C3 0.42" OLED 板(SSD1306 72×40,**SDA=GPIO5 / SCL=GPIO6**,0x3C;原生 USB;4MB Flash) | USB-C |
| 射频 | YS-RF34DL 315/433 编解码模块(STC15 主控,3.2×2.5×1.2cm) | TTL 串口 9600 8N1 |

**代价(写死,不要在执行时忘掉)**:

- **没有本地按键**:板载 OLED(SSD1306 72×40,GPIO5/6)只做**状态显示**
  (READY / LEARN / RX / TX / 计数器),不能选码或发码;操作走串口/Web/BLE/uConsole。
  屏不在时固件静默降级为纯串口,不阻塞启动。
- **屏只有 72×40 / 12×5 字符**:只放状态,不镜像整条串口日志;不支持中文。
- **I2C 写屏是同步的**:整帧 361B,400kHz 实测 ~8.6ms(失败回退 100kHz)。
- **只做固定码**(EV1527 / PT2262/2260/2240 族):滚动码学不会,也测不了,不能据此断言滚动码设备安全。
- **没有发射硬门控**:模块常带电,固件每发出一条帧就是真的在发。旧方案的 `RF_KILL` 物理开关随三模块方案一起消失 —— 这是主动丢掉的一条安全能力。
- **模块行为不完全公开**:发射时长单位、应答时机、学习码写入方式均无文档,只能实测标定。

## 4. 供电与电平 —— ★ 本文档最大的未定项

模块说明书自相矛盾:

| 出处 | 写的 |
|---|---|
| 核心参数 | 工作电压 DC **3.3–5V(宽电压)** |
| 引脚定义 | VCC **4.5–5.5V** |
| 应用举例 | 接单片机「**需要外加 3.3V 转 5V**」 |

**决策:按 3.3V 直连**(VCC 与 TTL 同电压)。

**理由**:VCC 与逻辑电平必须一致。若 5V 供电,模块 TXD 输出 5V,而 ESP32-C3 的 GPIO 绝对最大只有 3.6V(**会打坏**);同时 ESP32 的 3.3V TX 低于 5V TTL 的 VIH(≈0.7×VCC = 3.5V),模块收不到可靠高电平。3.3V 下两侧天然匹配,零额外器件。

**代价 / 风险**:

- 3.3V 落在「核心参数」内,但低于「引脚定义」的 4.5V,**发射功率与距离没有保证**;模块内部升压到 10V 是否够劲,只能实测。
- 2026-11-15 已按 **3V3 直连**上机:收发、改波特率、应答全部正常,学习型遥控器也学到了发射码(见 §11)—— 「3.3V 能工作」已被证实;**距离**仍未测。

**升级路径(仅当实测距离不够)**:改 5V 供电 + `TXD` 串 1kΩ/2kΩ 分压到 GPIO4 + ESP32 的 `GPIO3` 经 5V 缓冲(74HCT1G125 或 BSS138 电平转换)→ 模块 RXD,共地。这是**改接线,不是换方案**。

**禁止**:5V 直接接 GPIO4/GPIO3;上电前必须量模块 TXD 空闲电压(应 ≈3.3V)。

## 5. 模块串口协议(已被实测确认)

帧长固定 **8 字节**,`FD` 开头、`DF` 结尾;第三个字节在两个方向含义不同。

### 5.1 发射

| 用途 | 帧 |
|---|---|
| 315M 发射 | `FD F3 03 c0 c1 c2 c3 DF` |
| 433M 发射 | `FD F4 03 c0 c1 c2 c3 DF` |
| 315M 长发 | `FD F3 FE c0 c1 c2 c3 DF` |
| 315M 停止 | `FD F3 FF c0 c1 c2 c3 DF` |

第三字节 `03` 是「发射持续时间」(单位未给);`FE` 长发、`FF` 停止。

### 5.2 解码输出

| 频段 | 帧 |
|---|---|
| 315M | `FD F3 03 c0 c1 c2 c3 DF` |
| 433M | `FD F4 03 c0 c1 c2 c3 DF` |

第三字节固定 `03`;`c0..c3` 是解码得到的 4 字节「遥控器信息」,**原样存、原样回放**,固件不解析 EV1527 的地址/按键位。

### 5.3 配置与应答(延迟为 2026-11-15 实测)

| 命令 | 帧 | 应答 | 应答延迟 |
|---|---|---|---|
| 设 4800 | `FD 01 F1 00 00 00 00 DF` | `F1` | — |
| 设 9600 | `FD 02 F1 00 00 00 00 DF` | `F1` | ~0.15s |
| 设 57600 | `FD 03 F1 ... DF` | `F1` | ~0.10s |
| 设 115200 | `FD 04 F1 ... DF` | `F1` | — |
| 单次输出 | `FD 01 F2 ... DF` | `F2` | ~0.05–0.15s |
| 连续输出 | `FD 02 F2 ... DF` | `F3` | ~0.05–0.15s |
| 单帧发射(dur=03) | `FD F3 03 … DF` | `F0` | **~0.85s** |
| 长发(dur=FE) | `FD F3 FE … DF` | `0xFE` 心跳 | 首拍 ~0.17s,之后 **~25Hz** 重复 |
| 停止(dur=FF) | `FD F3 FF … DF` | 可能先一个在途 `0xFE`,再 `0xFF` | ~0.02–0.05s |

**要点**:`F0` 明显晚于 `F1/F2/F3`(0.85s vs 0.1s),等待窗口必须 ≥1s,否则会把成功报成失败。
长发/停止**不回 `F0`,但也不是"无应答"**:长发期间模块以约 25Hz 发 `0xFE`,
`STOP` 后发一个 `0xFF` 并停止。0.4.0 曾用 `MON` 判为"确实没有回包" —— 那是**错误结论**,
已由 2026-11-15 的 OLED 计数器暴露并复测修正,见 §11.2 与
[`evidence/2026-11-15-oled.md`](evidence/2026-11-15-oled.md) §4。

### 5.4 实测证据(2026-11-14,真模块)

9600 8N1,最短脉宽 104µs;按遥控器收到(16 字节 = 同一帧连发两次):

```
FD F3 03 55 55 03 3C DF  FD F3 03 55 55 03 4B DF
```

即:**315M**,两个按键的码分别是 `5555033C` / `5555034B`(低字节不同)。这条抓包是「文档帧格式 = 模块实际输出」的现场证据。

### 5.5 说明书里已知的矛盾(以实测为准)

| # | 矛盾 | 处理 |
|---|---|---|
| 1 | 供电 3.3–5V vs 4.5–5.5V | 按 3.3V 接,见 §4 |
| 2 | FAQ 说「F0 F0 … 共 8 字节」 | 实测是 `FD … DF`,以实测为准 |
| 3 | FAQ 的命令写成 `0x0F, 0x01, 0xF2…` | 疑 OCR 错误,实际是 `0xFD` |
| 4 | 「03 代表发射持续时间」无单位 | 默认用 03;长发/停止用 FE/FF |
| 5 | 学习码存 20 个,但没给写入触发方式 | 本版**不使用**模块侧学习存储,只用解码输出 |
| 6 | 应答是单字节还是帧、在哪个波特率发出 | **已实测**:单字节;`F1/F2/F3` 约 0.1s,`F0` 约 0.85s;`FE` 长发心跳 ~25Hz,`FF` 停止;改波特率时 `F1` 落在旧波特率上 |

## 6. 固件行为

| 命令 | 作用 | 正常返回 |
|---|---|---|
| `HELP` | 命令表 | — |
| `INFO` | 固件/模块波特率/OLED 状态/计数(stray、resync 是「可见失败」的度量) | `OK stored=…` |
| `LIST` | 列出已存码(格式不变) | ` 1  315M 5555033C` |
| `LIST LONG` | 列出码 + 名称/分组/符号/标记(人类可读) | ` 1  315M 5555033C  name="客厅大门" …` |
| `SEND <id>` | 发射一次(dur=03) | `OK tx id=1 band=315M code=… (0xF0, 850ms)` |
| `LONG <id>` | 长发(dur=FE) | `OK long … (0xFE, ~170ms)`;之后模块持续发 `0xFE` 心跳 |
| `STOP <id>` | 停止发射(dur=FF) | `OK stop … (0xFF, ~23ms)` |
| `ERASE <id|all>` | 删除 | `OK erased …` |
| `MODE single\|continuous` | 模块解码输出模式 | `OK mode=…` |
| `BAUD <n>` | 改模块波特率(4800/9600/57600/115200) | `OK baud=…` |
| `RECOVER` | 扫模块波特率并强制回 9600 | `OK module baud=9600` |
| `RAW <hex>` | 向模块注入任意字节(调试) | `OK raw n B` |
| `MON ON\|OFF` | 逐字节 hex 打印模块数据(调试) | — |
| `ECHO ON\|OFF` | 是否打印解码事件 | — |
| `WIFI [status]\|[ssid pass]\|CLEAR` | 配 STA / 忘记 STA;凭据存 NVS | `OK wifi …` |
| `BLE [on\|off]` | BLE 广播开关/状态 | `OK ble=on adv=…` |
| `PIN` | 显示 BLE 4 位 PIN(**仅串口**) | `OK ble_pin=…` |
| `STATE` | 打印 JSON 状态快照 | JSON |
| `WEBTEST` | 设备内自测 HTTP `/api/hello`、`/api/events`、POST `/api/cmd` | `OK webtest …` |
| `DISP ON\|OFF` | 开/关板载 OLED(显存保留) | `OK disp=…` |
| `DISP TEST [s]` | 几何测试图案,默认 10s,到期自动回状态页 | `OK disp=test Ns` |
| `DISP SHOW` | 把当前帧缓冲打成 72×40 `#/.` ASCII(不读玻璃) | `OK fb 72x40` |
| `RESET` | 重启 ESP32 | — |

规则:

- **学码是自动的**:模块一直处于接收态,按遥控器即输出帧;固件把新码入库(NVS,最多 32 条)并打印 `LEARN id=N …`。同码 600ms 内只算一次(实测一次按键会连出多帧)。
- **码库 v2(0.7.1)**:每条码增加 name/group/sym,存 NVS `codes2`;旧 v1 `codes` 保留作迁移/回滚兜底。名称/分组/符号按 UTF-8 字节上限校验,超长/非法 UTF-8 拒绝,不静默截断;串口只能输 ASCII,Web/BLE 可输中文。`NAME/SYM/GROUP` 空参数即清除。`NEW` 与 `EDIT` 拒绝重复 `band+code`,长发进行中拒绝改 band/code;NVS 写失败回滚并打印 `ERR`,不报假 OK。
- **启动时不给模块发任何配置命令**:模块行为未公开,少发一条就少一个假证据源;`MODE`/`BAUD` 只在用户显式要求时发。
- **等应答**:`SEND` 等 `F0` 最多 1500ms(实测 0.85s);`LONG` 等首个 `0xFE`;`STOP` 等 `0xFF`。收到打印 `OK …`,没收到才打印 `WARN … no 0xNN`(不静默)。
- **OLED 是纯输出**:启动时 probe 0x3C;成功则显示状态页,失败只打印 `# oled …` 并继续,串口行为与 0.4.0 一致。默认开;`DISP OFF` 关屏,`DISP ON` 恢复。
- **刷新策略**:事件驱动 + 最多 10Hz;整帧 361B @400kHz 实测 ~8.6ms(初始化失败自动回退 100kHz)。末行 `F/A/S` = 帧数 / 应答数(含 `FE` 心跳) / stray。
- **状态页**:5 行 × 12 字符,固定标题/频段/码/结果/计数;`DISP SHOW` 可把同一帧缓冲打成 ASCII 复核。
- **发射优先**:模块自身规定解码期间收到发射命令优先发射,固件按顺序写,不做额外调度。

AC-6 的「原接收器动作」由**更硬的证据**替代:**学习型遥控器**对准模块学到了 `5555034B`,再按它时模块解回同一个码 —— 说明空中链路真的发出去了,不只是 UART 收了个 ACK。

## 8. 不做

| 不做 | 原因 |
|---|---|
| 滚动码克隆/重放 | 模块只输出固定码;需要裸 OOK 捕获,另案 |
| 原始 OOK 波形记录/分析 | 同上;这版连射频引脚都没有 |
| 扫频 / RSSI / 频谱 | 模块不提供,也没有可编程射频前端 |
| Wi-Fi/BLE 做 315/433 射频 | 只做控制 UI;315/433 的调制/解码/发射仍由 YS-RF34DL 负责 |
| OLED 菜单/按键交互 | 屏只做状态输出;板载按键不参与选码/发码;交互走 Web/BLE/TUI |
| OLED 中文/图形界面 | 5×7 ASCII、12×5 字符,够状态用;不做 UI 框架 |
| 解析 EV1527/Princeton 位结构 | 模块只给 4B payload;码库原样存/改/发,不做协议推断 |
| 编辑模块 TX 时序/第三字节 duration | `03/FE/FF` 是长发/停止语义,单位未公开;改它属于射频行为,另案 |
| Flipper `.sub` 导入 | `Protocol/Bit/Key/TE` 到本项目 4B 的映射未实测;先只做自有 JSON/NVS |

## 11. 上机记录(2026-11-15)

ESP32-C3 0.42" OLED + YS-RF34DL,VCC **3V3 直连**,模块 TXD→GPIO4 / RXD→GPIO3,主机 Linux 经原生 USB CDC。

### 11.1 0.4.0 首跑

逐条命令、时间戳与原始观察见 [`evidence/2026-11-15-bringup.md`](evidence/2026-11-15-bringup.md)。

| 结论 | 依据 |
|---|---|
| 学码 3 个键:`5555034C` / `5555033C` / `5555034B`,均 315M | 按原遥控器时的 `LEARN id=1..3` |
| 发射 15/15 成功 | 每次 `SEND` 都在 ~0.85s 收到 `F0` |
| **空中链路成立**(不只是 UART ACK) | 学习型遥控器学到 `5555034B`,再按它时模块解回同一个码 |
| 波特率可改 | `BAUD 57600` → `SEND` → `BAUD 9600`,两段都收到 `F1` |
| 长发/停止不回 `F0` | `MON` 确认没有 `F0`。**但"没有回包"是错的**:0.5.0 实测有 `0xFE/0xFF` 状态字节,见 11.2 |
| 一次异常:教学期间 `stray` 累积 72 字节 | 之后 5 次正常按键 `stray` 不变、帧全长 8 字节干净;仍未复现,与本节的 `0xFE/0xFF` 不是同一现象 |

### 11.2 0.5.0:OLED 上机 + 长发/停止修正

逐条记录(含 `DISP SHOW` 的 40 行 ASCII 与反解文本)见
[`evidence/2026-11-15-oled.md`](evidence/2026-11-15-oled.md)。

| 结论 | 依据 |
|---|---|
| OLED 在线:0x3C,400kHz,无 I2C 错误 | 启动 `# oled …: ok`;`INFO` `present=yes err=0`,整帧 ~8.6ms |
| 几何正确:列偏移 28、页 0..4、方向正常 | `DISP TEST 300` 四边完整、文字正常,**用户目视确认** |
| 学码页/RX 页/发射页随事件更新 | 屏上反解出 `LEARN ID 5 / 433M / …`、`RX ID 2 / 315M / 5555033C`、`TX ID 1 OK / F0 821ms` |

## 12. OLED 本地显示:决策与代价(0.5.0)

**根因**:0.4.0 把板载 72×40 OLED 延后,设备上有一块屏却没有任何本地状态出口;
不接主机就看不到 READY、学码结果、发射成败,也看不出模块是否在线。0.5.0 的 OLED
计数器还把 0.4.0 的"长发/停止无回包"结论暴露成错误(§5.3)。

**关键判断**:

- 只做**状态页**(5 行 × 12 字符),不做串口日志镜像 —— 72×40 放不下日志,滚动文本不可读。
- 分层:`oled_gfx`(纯帧缓冲 + 5×7 字库)、`ui`(纯状态→文本)、`oled`(仅 I2C/SSD1306);
  前两层可在主机单测,驱动只上机验证。帧缓冲 360B,字库 475B。
- 几何取 **U8g2 72×40 ER** 的初始化序列 + **Zephyr 01Space** 板级参数:
  列 28..99、页 0..4、MUX 0x27、COM 0x12、内部 IREF `0xAD/0x30`。
- I2C **400kHz**,初始化失败回退 **100kHz**;整帧 361B 实测 ~8.6ms,事件驱动 + 最多 10Hz,
  只在脏状态时写屏,避免挤占 `F0` 的 0.85s 等待窗口。
- probe 失败/写屏失败**不阻塞、不重启、不重试风暴**;串口行为回到 0.4.0,`DISP SHOW` 仍可在 RAM 里复核。

**避免的误修**:

- ❌ 把整条串口控制台镜像到 OLED:12 字符宽会碎成滚动噪声,还把显示耦合到日志格式。
- ❌ 引入 u8g2/Adafruit 整套图形库:只为状态页,依赖、初始化差异和移植成本不划算;
  自备 5×7 字库 + 360B 帧缓冲,只借用参考参数。
- ❌ 把屏当必需件:初始化失败就报错/重启,会让"没有屏的板"失去串口工具能力。
- ❌ 固定 100kHz 图省事:整帧约 32ms,10Hz 下占用明显;400kHz 实测可用,失败再降速。
- ❌ 把 `0xFE` 心跳当 stray:那会把模块的正常长发状态记成"可见失败";已改为 ACK,`stray` 只留真异常。

**代价**:

- 只有 5×7 ASCII,不支持中文;12×5 字符,信息量有限。
- 没有按键,屏不能交互;状态页不能替代串口命令。
- I2C 写屏是同步阻塞:最坏 10Hz、每次 ~8.6ms,发射瞬间屏幕会晚 ~9ms 更新。
- 构建体积(0.5.0,PlatformIO 汇总):Flash 221,594B(5.3%),RAM 9,836B(3.0%);
  这是整镜像数字,未单独剥离 OLED 的增量。

## 13. 跨平台 UI(0.6.0 起,0.7.1 扩展码库)

详细规格与传输契约见 [`01-ui.md`](01-ui.md)。本节只记录它对射频规格的边界:

| 项 | 结论 |
|---|---|
| Web | ESP32-C3 上 `esp_http_server`,单页内嵌 gzip;STA 成功时走 LAN IP,失败/配网时 AP `RF-Lab-XXXX` / `rflab1234` / `192.168.4.1` |
| BLE | NimBLE 外设,自定义 NUS 风格 GATT;应用层 4 位 PIN;不改变 315/433 链路 |
| Android | 同一份 Web UI + WebView + BLE 桥;APK 可侧载 |
| uConsole | `tools/rflab_tui.py`,HTTP 优先、串口回退;键盘操作 |
| 对射频的影响 | 无。命令最终仍走 §6 的 `SEND/LONG/STOP`;`F0`≈0.85s、`FE`≈25Hz、`FF` 已复测 |
| 已上机 | STA 接 `SSID-A`、LAN 浏览器/HTTP/SSE/POST、重启 AP 关闭;AP 回退 15/15 |
| 未验证 | STA 运行中掉线回退、外部浏览器经 AP、真实手机 BLE、Android 真机、uConsole 真机 |

**为什么不在 C3 上做第二套业务逻辑**:0.5.0 的命令时序(`F0` 0.85s、`FE/FF`)是上机
验证过的;Web/BLE 只做「一行命令 + 事件/快照」,避免复制一份会漂移的协议实现。

**代价**:STA 失败时最多等 15s 才打开 AP;APSTA 配网期间 AP 与 STA 同信道,吞吐/功耗略增;
**HTTP 无登录,AP 密码就是门槛**(STA 模式下则是局域网可达);BLE 无链路加密,只有应用层 PIN;
Web 的 ARM 只是防误触,不是硬门控。

## 14. 码库 v2:名称 / 分组 / 原始参数(0.7.1)

**根因**:0.7.1 之前的码库只有 `id / band / 4B code`,现场无法区分「客厅大门」和「车库卷帘」,
也不能手工补一条已知码;改原始参数只能靠重学。0.7.1 把码库从「匿名数组」升级为「带元数据的记录」。

| 字段 | 上限 / 值 | 说明 |
|---|---|---|
| `band` | 315 / 433 | 现有 |
| `code[4]` | 4B | 现有;原样 8 hex,不解析 EV1527/Princeton |
| `name` | 24B UTF-8 | 约 8 个汉字;空 = 未命名 |
| `group` | 16B UTF-8 | 单分组;空 = 未分组 |
| `sym` | 8B UTF-8 | 约 2 个 emoji;空 = 无 |
| `flags` | bit0 manual / bit1 edited | 手工建码 / 建码后改过 band 或 code |

单条 57B,32 条 blob ≈1.8KB;NVS 分区 24KB。v2 写 **`codes2`**(magic `R3`,ver 2),
v1 `codes` 原样保留;启动优先读 v2,缺失才迁移 v1,写后读回校验。

**关键判断**:

- **不改 `LIST`**:`LIST` 仍只输出 `id band code`,保护 AC-20/UI-6 的串口回归;
  新信息走 `LIST LONG`。任何新增元数据都不得让脚本/旧客户端解析错位。
- **id 仍是位置号**:分组只是视图筛选,不排序、不重编号;`ERASE` 后 id 前移是既有行为。
  这样 `SEND 3` 的语义不变;代价是并发删除时客户端要重新拉 `/api/codes`。
- **迁移独立 key + 保留 v1**:回滚到 0.6.x 仍能读旧码(但看不到 v2 的改名/删除);
  代价是 v1 会过期,不能当作 v2 的备份。
- **学习码允许直接改 band/code**:与手工码同一路径;UI 二次确认 + 原始帧预览 + 重复码检查,
  保存后不可撤销。`edited` 只作显示,不阻止发送。
- **NVS 写失败回滚**:保存函数返回 bool,变更前备份;失败恢复内存并打印 `ERR`,
  不再出现「界面显示已保存、重启丢失」的假 OK。

**避免的误修**:

- ❌ 直接把 `store_t` 改成 v2 后还按 `len == sizeof(st)` 判断:旧 blob 被当空库,9 条码消失。
- ❌ 只写同一个 `codes` key:迁移掉电窗口会同时覆盖 v1。
- ❌ 用宽松 `parse_hex` 处理 `NEW/EDIT`:它会跳过非 hex 字符,把脏输入当成合法码。
- ❌ 名称超长静默截断:中文可能被截半个码点,JSON 也会坏;必须拒绝并返回明确错误。
- ❌ 把分组做成排序/重排:会改变 `id`,让进行中的客户端发错码。

**边界**:不解析协议位结构、不暴露模块 TX 第三字节/时长、不做 `.sub` 导入;
HTTP 无登录,码库编辑不构成新的权限边界。
