## 1. 背景与问题

原产品定义列出五个核心场景,其中 **`S1 远程部署`** 是唯一一个"**设备与人分离**"的场景:

> 设备放在**车内/背包**中,接入现场路由器 Wi-Fi;人在**远处**用手机 App 远程控制扫频、解码、发射。

这个场景并非一个普通的使用方式,它是**一批设计要求的唯一来源**:

| 由 `S1` 派生的要求 | 在哪里被引用 |
|---|---|
| 约束 **`C-05`**「设备放置远处时无人值守」→ 看门狗、状态恢复、超时保护 | 产品定义 §4、固件文档 §10 长稳测试 |
| **设备侧离线记录 → 回读**(App 不在场时由设备独自记录数小时) | 契约 §9.1、App 文档 §2.4 / §9-10 —— 长期作为**未决项 Q-09** 挂着 |
| Wi-Fi/WebSocket 通道的定位 =「**远程**、高吞吐」 | 产品定义 §6.3、架构文档 §5、App 文档 §2.1 |
| App 侧"后台保活"需求(App 息屏后仍要持续收 `SCAN_HIT`) | App 文档 §1.4 / §2.4 |

2026-09-21,用户决定**取消无人值守功能**。

---

## 2. 决策

### 2.1 取消该场景,使用前提收缩为一句话

> **设备与手机同处一室,操作者在场,并在操作期间与设备保持连接。**

- `S1` 从核心场景中**移除**;`S2`–`S5` 保留,**编号不回填**(`S1` 永久空缺)—— 重排会破坏其他文档中已有的引用,而收益只是"编号连续"这一美观诉求。
- 由此,产品的全部使用方式都是**交互式、前台、有线/近距**的。

### 2.2 **不**取消 `C-05` 名下的任何工程手段(本 ADR 最关键的一条)

`C-05` 这个**约束条目**取消,但它的三条手段 —— **看门狗、状态恢复、超时保护** —— **一条都不删**。原因是它们的**真实职责从来不是"无人值守"**,而是:

> **防止设备在失去控制链路之后仍滞留在发射态。**

职责被重新表述后,要求反而**更严**了:取消无人值守意味着"**操作者在场且连着线**"成了发射的**充分前提**;既然每次发射都必然有人在场且连了线,那么"**链路一断就必须停**"就从一个"事后补救措施"升格为**首要防线**。

据此新增两条成对的硬要求(已写入固件文档 §9 与验证计划):

| 规则 | 内容 |
|---|---|
| **无活动链路即不得滞留发射态** | 三条链路(Wi-Fi / BLE / USB)**全部**断开 ⇒ 固件必须在 **2s 内**强制 `enter_idle()` + 拉低 `RF KILL`,**不得**"等待重连"。必须有**独立于链路**的兜底实现(`session` 最后活动时间戳 + `monitor_task` 轮询)—— 否则该前提本身就依赖链路 |
| **单链路断开不得中止发射** | 只要**还有一条**活动链路存活(例如操作者正看着有线侧),发射**继续**。防止把规则实现成"随便掉一条就停" |

两条必须**同时**成立,才说明实现的是"**有没有链路**"这个正确判据(验证计划 **TC-054 / TC-054a**)。

### 2.3 「设备侧离线记录 / 回读」转为**非目标**(Q-09 关闭)

该能力的**唯一**存在理由是"App 不在场时设备独自工作"。前提消失 ⇒ 能力无场景。

- 契约 **§9 非目标**显式登记;**不新增**"记录会话 → 回读"消息对
- 原 §9.1 的重复登记**删除**,避免同一件事两个 owner
- ⚠️ **不要再把它当待办**:它现在需要的是"重开无人值守这个产品决策",而不是"补一对协议消息"

### 2.4 取消**不**改变的部分

| 项 | 是否改变 | 说明 |
|---|---|---|
| 发射需人工二次确认、四道门禁、全量审计 | ❌ 不变 | 与在场与否无关 |
| 2.4GHz 满功率、功率可由 App 调节(C-11/C-12) | ❌ 不变 | 屏蔽室前提未变 |
| USB 为唯一可信配对信道(NQ-01 方案 A) | ❌ 不变 | 反而更自洽:配对本就要求在场 |
| OLED 延期(C-07 ⏸) | ❌ 不变 | 其三项职责的缺口仍在(产品定义 §7.1) |
| 看门狗 / 断连归 idle / 状态恢复 | **✅ 保留且强化** | 见 §2.2 |
| Wi-Fi 通道的**存在** | ⚠️ 未决定 | 派生新待决项 **NQ-04**,见 §5 |

## 4. 备选方案与否决理由

| 方案 | 理由 |
|---|---|
| **A. 取消无人值守,同时保留全部安全网(选定)** | 场景需求本就来自用户;取消后设计反而收窄、更可测。保留安全网使"设备不会在无人看管时发射"成为**可验证**的性质 |
| B. 保留无人值守,但把记录责任交给设备侧 | 需要新增一对协议消息 + 环形日志容量 + 分页口径,而换来的能力**用户已明确表示不需要**。且设备侧记录的权威性、掉电保持、时间基准(无 RTC)每一项都是新风险 |
| C. 只删场景文案,不动任何下游要求 | **最危险**。会留下"为不存在的场景服务的实现"与"无人验证的安全网"两类债;且 `C-05` 一旦被视为"已取消",看门狗/超时会被顺手删掉 —— 而它们与无人值守本就无关 |
| D. 取消无人值守,并同时删掉 Wi-Fi/WebSocket 全套 | 看似顺理成章(远程理由没了),但**取舍未做**:USB 已是主通道,Wi-Fi 作为同室高吞吐仍有价值。**降级为待决项 NQ-04**,不在本 ADR 内合并决策 |

## 5. 风险与未决

| ID | 项 | 严重度 | 处置 |
|---|---|---|---|
| **NQ-04** | **取消无人值守后,Wi-Fi/WebSocket 是否仍需要保留?** | 中 | **开放**。删除可一次性省掉 `wss` 信任模型这一整块在 PWA 上**无解**的难题(App 文档 §1.3)、设备 AP、`SET_NET` 配网流程。**建议:实现阶段先只做 USB + BLE,Wi-Fi 推到 v1.2** |
| **无人值守被"顺手恢复"** | 未来若不查本 ADR 就重新引入"设备自己挂机",会连带复活离线记录/回读与远程通道要求 | 中 | 契约 §9 已把它写成**显式非目标**并注明"须先改产品定义再回来加协议" |
| **安全网被误删** | "取消无人值守"极易被读成"看门狗/超时不必做了" | **高** | 本 ADR §2.2 + 产品定义 §2.4 的双重显式警示;TC-054 **升为必过项**使其不可被静默移除 |
| **断连判定本身失效** | 若"无链路⇒停发"的兜底实现依赖某条链路,则该规则在链路全断时失效 | **高** | 要求实现为**独立于链路**的时间戳 + 轮询(固件文档 §9);TC-054 要求**三条链路同时断**并断言射频零输出 |

## 6. 复议触发条件

出现下列任一情况,应重新评估本决策:

1. 用户重新提出**任何**"设备与人分离"的使用方式(远程、挂机、定时任务)——那时须先改产品定义 §2 与 §2.4
2. 出现"操作者**不能**与设备同室"的**现实**约束(如屏蔽室内不允许人员停留、设备需置于强场区外)
3. `NQ-04` 决定删除 Wi-Fi 通道 —— 那会使本 ADR §3 中多处"Wi-Fi"表述需要再收一次
4. 实测发现"三条链路全断"在某些合法操作序列下**必然发生**(例如换线、切通道的瞬间)——那说明 2s 门限或"活动链路"的定义需要改,而不是取消规则
