# ADR-0001:119–1050MHz 扫频需求与现有模块的覆盖空白

- 状态:`accepted`(**2026-09-20 用户决策:不增补模块,接受覆盖空白**;见 §5)
- 日期:2026-09-20(2026-09-20 修订:拿到泽耀科技官方手册,修正原推断;2026-09-20 定稿)
- 决策者:用户(产品所有者)
- 影响面:硬件选型、BOM、协议契约 `CAPS.bands`、App 扫频 UI、**需求 F-01 的措辞与判据 A-02/A-06**

## 1. 背景与问题

产品需求 F-01 写明:

> 自动扫频:在 **119–1050MHz** 范围内快速扫描,检测 RSSI 超阈值的信号。

而需求给定的三个射频模块,其频率能力经**厂商官方手册**核实为:

| 槽位 | 模块 | 芯片 | **模块级**实际频率能力 | 来源 |
|---|---|---|---|---|
| 1 | AS10-M4463D-SMA | SI4463 | **425–525MHz**(软件可调) | [官方手册 as10m4463dsmacn.pdf](http://www.ashining.com.cn/data/as10_m4463d_sma.zip) §四 |
| 2 | AS07-M1101D-SMA | CC1101 | **387–464MHz**(软件可调,推荐 433±10MHz) | [官方手册 as07m1101dsmacn.pdf](http://www.ashining.com.cn/data/as07_m1101d_sma.zip) §四 |
| 3 | AS01-ML01 | nRF24L01P + RFX2401C | 2400–2525MHz(126 信道) | [官方手册 as01ml01cn.pdf](http://www.ashining.com.cn/data/as01_ml01.zip) |

芯片级能力(用于判断"能否靠换模块/改匹配网络扩展"):

| 芯片 | 芯片级频率能力 | 来源 |
|---|---|---|
| SI4463 | **142–1050MHz**(全系列,不分版本) | [Si446x 数据手册 Rev 1.4](https://www.silabs.com/documents/public/data-sheets/Si4464-63-61-60.pdf) §Summary |
| CC1101 | **300–348 / 387–464 / 779–928MHz**(三个分立子带) | TI CC1101 数据手册(本仓库已存档于模块资料 zip) |
| nRF24L01P | 2400–2525MHz | Nordic |

### 2.1 Q-01 的结论:**原推断被证伪**

原 §1 曾据一个**二手来源**推断"SI4463 有 C2A / B1B 两个频率版本,该模块搭载 B1B,故只能 425–525MHz"。**取得官方资料后,该推断是错的**:

1. **Si446x 数据手册全系列写 `Si4463 = 142–1050MHz`,没有任何按版本划分的频率区间**;文档里 `Si4463-Bxx-FM3` 的编码规则说明 `Bxx` 是 *ROM 版本 + 固件版本*,与频率无关。
2. Silicon Labs 自家规格页明确写着 **"Si4x6x-C2A 无线电代表了最新一代的 EZRadio"** —— C2A 是**更新**的代次,并非窄带老型号。
3. 官方手册写明 AS10-M4463D-SMA 工作频段 **425–525MHz**,且 AS10 系列另有 **915MHz 型号**(`AS10-M4463D-915SMA`),载波频率列在**模块型号**行而非芯片行。

> **⇒ 真正的约束是模块级前端,不是芯片版本。** AS10-M4463D-SMA 只到 425–525MHz,是因为厂商按 433MHz 设计了匹配网络与滤波,**换一颗"C2A 版芯片"并不会让这块模块变宽**。
>
> **这同时告诉我们正确的解法**:要覆盖 142–1050MHz,需要的是**模块级 142–1050MHz 前端设计**(或选用厂商的宽覆盖型号),而不是换芯片版本。

**遗留**:厂商未公开 AS10 的匹配网络能否重调至更宽频段;问厂商"是否有宽频版本或定制可能"仍值得一问,但**不再是阻塞项**。

## 2. 覆盖分析(按官方模块级数据)

| 频段区间 | 覆盖模块 | 状态 |
|---|---|---|
| 119 – 300MHz | 无 | ❌ **空白**(共 181MHz) |
| 300 – 348MHz | CC1101 芯片可及,但 **AS07 模块未覆盖**(其带内下限 387MHz) | ❌ **模块级空白** |
| 387 – 425MHz | CC1101(AS07) | ✅ |
| 425 – 464MHz | CC1101(AS07) + SI4463(AS10) | ✅ 双覆盖 |
| 464 – 525MHz | SI4463(AS10) | ✅ |
| 525 – 779MHz | 无 | ❌ **空白**(共 254MHz,最大缺口) |
| 779 – 928MHz | CC1101 芯片可及,但 **AS07 模块未覆盖**(其带内上限 464MHz) | ❌ **模块级空白** |
| 928 – 1050MHz | 无 | ❌ **空白**(共 122MHz) |
| 2400 – 2525MHz | nRF24L01P(AS01) | ⚠️ 在 119–1050 需求之外 |

**结论:模块级真实覆盖仅 387–525MHz 共 138MHz,约占 119–1050MHz 带宽(931MHz)的 15%。**
三块空白(119–300、525–779、928–1050)合计 557MHz。

> ⚠️ **比上一版更糟,而且是被官方资料确认的更糟**:上一版按"CC1101 三子带全覆盖"估算约 40%,现已知 **AS07 模块把 CC1101 裁剪到 387–464MHz**,故 300–348 与 779–928 两段**在模块层面也不可用**(除非重调前端或换用未裁剪的 CC1101 模块)。


## 3. 关键区分:芯片能覆盖 ≠ 模块能覆盖 ≠ 能测到信号

**这三级区分现在有了硬证据**(此前只是设计原则):

| 层级 | 证据 |
|---|---|
| **芯片级** | SI4463 = 142–1050MHz;CC1101 = 300–348/387–464/779–928MHz |
| **模块级** | AS10-M4463D-SMA 被**裁剪到 425–525MHz**;AS07-M1101D-SMA 被**裁剪到 387–464MHz** |
| **可用级** | 还要再过天线带宽与匹配网络这一关 |

**SI4463 是最好的例子**:芯片明明能到 142–1050MHz,而搭载它的 AS10 模块只给 425–525MHz —— **中间差的 600MHz 完全是模块前端设计拿掉的**。同理 CC1101 芯片有三段,AS07 模块只留下中间一段。

其余两条仍然成立:

1. **匹配网络与滤波**:模块的巴伦/匹配网络与谐波低通滤波器按目标频段设计。把 425–525MHz 的模块拿到 119MHz 或 1050MHz,驻波与灵敏度都会严重劣化,**发射更是不能碰**。Silicon Labs 的 [AN648(PA 匹配)](https://www.silabs.com/documents/public/application-notes/AN648.pdf) 说明匹配网络必须针对频段单独设计——这正是"芯片能力被模块砍掉"的物理原因。
2. **天线带宽**:SMA 天线的带宽远小于模块的调谐范围,一支 433MHz 天线在 315MHz 与 915MHz 上效率极低。
3. **"扫频"的真实含义**:本产品的扫频是**逐点调谐 + 读 RSSI**,不是宽带 FFT。扫描速度受"调谐时间 + 驻留 + RSSI 读取"限制,不是示波器式的瞬时全覆盖。

因此**任何"119–1050MHz 全覆盖"的宣传都需要前端硬件支撑,不能靠软件调谐实现**。

## 4. 候选方案

### 方案 A:诚实裁剪范围(最小改动)

把产品定义改为"覆盖模块实际支持的分立频段",在 App 中只展示真实可扫的区间;协议已支持这件事——`SCAN_DONE.coverage` 必须回传真实覆盖,超范围请求回 `WARN{band_clipped}`。

- ✅ 零额外硬件成本;✅ 立刻可落地;✅ 与协议契约天然一致
- ❌ 大幅偏离原始需求;❌ 缺失 868/915MHz 与低频段

### 方案 B:替换/新增宽覆盖 Sub-GHz 模块(推荐)

用一颗**连续覆盖更宽**的收发器替换或补充 M1:

| 候选 | 芯片 | 连续覆盖 | 发射 | 备注 |
|---|---|---|---|---|
| SI4432 | Silicon Labs | **240–930MHz 连续** | ≤20dBm | 一颗覆盖 CC1101 的全部断点(348–387、525–779),且能吃下 868/915MHz |
| **宽覆盖 SI4463 模块**(非 AS10) | SI4463 | 芯片可 142–1050MHz | ≤20dBm | **正确解法**:换**模块**而非换芯片版本——需找/定制 142–1050MHz 匹配网络的 SI4463 模块。AS10 做不到(按 433MHz 设计) |
| **宽覆盖 CC1101 模块**(非 AS07) | CC1101 | 芯片可 300–348/387–464/779–928 | ≤10dBm | AS07 被裁剪到 387–464;**未裁剪的 CC1101 模块**可拿回三段,成本低 |
| CC1125 / CC1200 | TI | 164–950MHz / 410–950MHz | ≤16dBm | 高性能窄带,适合远距 |
| 宽频对数检波器(如 AD8318 / LT5534) | ADI / LTC | 1MHz–8GHz | 仅接收 | **只能测能量,不能解调**;但可作"宽带 RSSI 哨兵"快速发现目标频点,再用窄带模块精调 |

- ✅ 能真正逼近 119–1050MHz;✅ 保留原有模块作为多频段/多协议对照
- ❌ BOM 成本与体积增加;❌ 低频端(119–142MHz)仍无覆盖,需另议
- ⚠️ **注意**:仓库中 AD8318/LT5534 的型号与频段**未经本仓库核实**,选型前必须查数据手册
- 📌 **采购提醒**:选型时必须看**模块手册的"工作频段"行,不是芯片手册** —— AS10/AS07 的教训就是只看芯片会高估 600MHz 以上

### 方案 C:分级产品定义(推荐与 B 组合)

把"扫频"拆成两个能力层级,分别对应两类硬件:

| 层级 | 能力 | 硬件 | 价值 |
|---|---|---|---|
| L1 宽带能量发现 | 快速找出"哪里有信号"(不认协议) | 宽频检波器 / 现有模块轮询 | 解决"范围"诉求 |
| L2 窄带解调识别 | 锁定频点,捕获时序、识别协议 | CC1101 / SI4463 / nRF24 | 解决"识别"诉求 |

这符合射频工程的真实做法,也让"119–1050MHz 快速扫描"这个需求有了一个**诚实的实现路径**:宽带发现用宽频前端,精细分析用窄带模块。

### 方案 D:不推荐——宣称全覆盖

用软件把超出能力的频段"扫一遍"并返回低 RSSI。这会产出**看起来正常但完全虚假**的扫描结果,对安防场景是危险的误导。**本仓库明确拒绝此路径**,并将其写入合规红线。

## 5. 决策

### 5.1 决策内容(2026-09-20,用户)

> **采用方案 A:接受覆盖空白,不增补任何模块。硬件已采购完毕(三块模块即最终配置)。**

即:**明确放弃**方案 B(替换/新增宽覆盖模块)与方案 C 的硬件部分(宽频检波器 L1 哨兵)。方案 D 一如既往被拒绝。

### 5.2 被放弃的选项(留档,以便日后重新评估时不必从零开始)

| 方案 | 若日后重启,首选路径 | 理由 |
|---|---|---|
| B | **未裁剪的 CC1101 模块** | 成本最低。CC1101 **芯片**覆盖 `300–348 / 387–464 / 779–928MHz` **三个子带**,而 AS07 模块只放开了中间一段 —— 换未裁剪模块可一次拿回 **300–348 与 779–928** 两段(§4 表) |
| B' | SI4432(240–930MHz 连续) | 单颗吃掉 240–930,覆盖跃升最大 |
| C | 宽频对数检波器(AD8318 类)作 L1 能量哨兵 | 只测能量不解调,但能把"哪里有信号"的范围诉求解决掉 |

> ⚠️ 上述型号的**具体模块**均未经本仓库核实;重启时仍须遵守 §3 的"查模块手册、不查芯片手册"纪律。

### 5.3 ⚠️ 本决策产生的**强制义务**:空白必须可见

接受空白**不等于**可以让设备对扫不到的频段保持沉默。这是本 ADR 最重要的一条落地要求:

> **设备对落在模块能力外的扫描请求,必须明确回报"扫不到",禁止返回空结果或低 RSSI 让 App 显示"该频段干净"。**

理由:用户买到手后**一定会**去试 315MHz 或 868MHz(遥控器/传感器的常识频段),而它们**恰好落在空白里**。若设备静默返回"无信号",用户会得出**"这个频段没有信号"的错误结论**——而真相是"**这台设备根本听不见这个频段**"。在安防/巡检场景下,这个区别至关重要,且属于**危险的误导**(与方案 D 被拒绝的理由同源)。

已落地的机制(全部在契约 v1.1 中):

| 场景 | 设备行为 | 契约依据 |
|---|---|---|
| 请求范围**完全**在能力外 | 回 `ERROR{band_out_of_range}`,不下发任何调谐命令 | §6 |
| 请求范围**部分**在能力外 | 回 `WARN{band_clipped}` + `SCAN_DONE.coverage` 给出**真实扫过的区间** | §3.3 |
| 任何情况 | `coverage` 必须是**模块级**真实区间,**禁止**上报芯片级频段或夸大范围 | §3.3「覆盖诚实性」 |

## 6. 后果

### 对协议契约的影响(已落地)

- `CAPS.modules[].bands` 必须回传**模块级真实**频段,而非芯片手册频段
- `SCAN_DONE.coverage` 必须回传真实扫过的区间
- 超范围请求必须 `WARN{band_clipped}`,**禁止静默裁剪**

### 对 App 的影响

- 扫频范围选择器必须由 `CAPS` 驱动,不得硬编码 119–1050MHz
- 遇到裁剪必须在 UI 明确告知用户"实际只扫了 X–Y"

### 对产品定义的影响

- 需求 F-01 的"119–1050MHz"已改写为"**覆盖所装模块的真实频段(387–525MHz),并在 UI 中如实呈现**"(见 010-product-definition F-01 与 C-08)
- 成功判据 A-02 的比对范围**收敛到 387–525MHz**
- **新增判据 A-06**:请求带外频段时必须明确回报"扫不到"(§5.3),且不得返回空结果冒充"无信号"

### 明确列为非目标(本决策的直接后果)

| 项 | 状态 |
|---|---|
| 119–300MHz 的扫描与发射 | ❌ **不在范围内**(硬件不可及) |
| 525–779MHz 的扫描与发射 | ❌ **不在范围内** |
| 928–1050MHz 的扫描与发射 | ❌ **不在范围内** |
| 868 / 915MHz(ISM) | ❌ **不在范围内**(落在 525–779 与 928–1050 空白内) |
| 315MHz 遥控器 | ❌ **不在范围内**(119–300 空白内) |
| 后续增补硬件以扩展覆盖 | ❌ 本期不做(§5.1) |

> **这些频段不是"暂不支持",而是"物理上不可及"。** 文档与 UI 都不得暗示可以覆盖——这正是 §5.3 强制义务要防的事。
