## 1. 背景与问题

两条各自独立的决策在 2026-09-21 汇合,指向同一个结论:

1. **`S1 远程部署` 已取消**(ADR-0004)⇒ Wi-Fi 的"远程"定位消失,只剩"同室高吞吐"。
2. **首次配对只走 USB**(`NQ-01` 方案 A)⇒ BLE 在本批**不承担配对职责**,且无屏时它只能回 `no_display`。

而**使用环境是屏蔽室**,其真实含义是:**设备与手机同处一室**。在这个前提下,"无线通道"的价值必须重新算账:

| 通道 | 同室前提下的真实价值 | 代价 |
|---|---|---|
| **USB** | 唯一**不受本机 20dBm 自扰**的通道(R-01);且是唯一可信配对信道 | **本批唯一通道 ⇒ 单点故障**(见 §4) |
| BLE | 同室近距免插线 | 本批**不能配对**;无屏时只能回 `no_display` |
| Wi-Fi | 同室高吞吐 | PWA 上 `wss://` 信任模型**无解**(需设备 CA 或内网域名+公信证书)+ 设备 AP + `SET_NET` 配网 + 密码面 |

用户决定:**本批只做 USB。**

## 2. 决策

### 2.1 本批的控制通道只有一条:USB

- 本批**固件不实现** Wi-Fi 协议栈、WebSocket 服务端、设备 AP、`SET_NET` 配网流程,亦不实现 BLE GATT 服务。
- 控制通道 = **ESP32-S3 原生 USB Serial/JTAG**(ADR-0003),引脚 GPIO19/20。
- 与之配套:首次配对**只经 USB**(`NQ-01` 方案 A,ADR-0003),`pairing_secret` 只经 USB 下发。

### 2.2 ⚠️ BLE/Wi-Fi 是**移出本批**,不是**从产品中删除**(本 ADR 最关键的一条)

用户明确选择"**只从本批移出,代码不写,能力定位保留**"。因此:

| 对象 | 本批处置 | **不得**做的事 |
|---|---|---|
| 场景 `S2 近距调试`(BLE) | ⏸ 标注**延后**,编号保留 | 不得删除场景定义或标记为"非目标" |
| `F-07`(Wi-Fi/WebSocket 控制) | ⏸ 延后,**不再是 P0** | 不得写成"取消" |
| `F-08`(BLE 控制) | ⏸ 延后 | 同上 |
| 契约的**承载章节**(§2.1 Wi-Fi/BLE 行、§2.2.1 的 `ble_frame_max` 推导、§2.3 BLE 分片) | **原样保留**,加 ⏸ 延后标注 | **不得删除或重推导** |
| `CAPS.limits.ble_frame_max` / `ble_frag_total_max` | **保留在 schema 中** | 不得删字段 |

**为什么必须保留能力定义**(而不是"反正不用了删掉更干净"):

1. **契约是"传输无关"的**(§1 明文"一份帧格式,三条传输")。若把 BLE/Wi-Fi 的承载定义删掉,契约就退化成"USB 专用协议",而 §2.2.1 那段 `ble_frame_max` 推导是**一次已经做完且算对了的推导**(它修正了两处旧口径错误)。删除 = 下次纳入无线时要**重新推一遍**,且很可能重蹈原错。
2. **schema 镜像要保持向后兼容**:删字段是对既有实现的不兼容变更,而本批**没有任何功能需要它**。保留一个"本批不使用但已定义"的字段,成本为零。
3. **延期与删除的语义差别是真实的**:延期意味着"能力定位仍在、只是本批不做";删除意味着"产品不要这个能力了"。**用户选的是前者** —— 文档若写成后者,会误导后续批次不去实现它。

> ✅ **由此得到一条可验证的豁免**:本 ADR **不改变任何 schema 字段**(仅可能改**描述文本**),因此**不产生契约字段级不兼容变更**。

### 2.3 设备侧指示:蜂鸣器**不存在**,只剩板载 WS2812

用户告知:**硬件没有蜂鸣器;开发板上有板载 LED**。

- BOM、接线图、GPIO 表里的**蜂鸣器(GPIO39)全部移除**。
- 「设备侧本地状态出口」(NQ-02 剩余部分)本批**唯一载体 = 板载 WS2812**。
- ✅ **2026-09-21 补记(同一日二次核实)**:该灯的 **GPIO 与类型已核实** —— **WS2812 单线可寻址,GPIO48**(见 F-4d-3)。本 ADR 原文写"尚未核实(F-4d-2 / V-13)"**已过时**,保留在此以显示核实路径。
- ⚠️ **核实结果反而加了一条纪律**:本 ADR 原文的假设是"指示语要对单色与 RGB 都成立"。核实后**该假设仍成立但理由变了** —— 不是因为"可能是单色",而是因为:①**颜色对色觉障碍者不可靠**;②**山寨板可能根本不焊 2812 信号**(R-18)。⇒ 语义由**闪烁时序**承载,颜色只作增强。
- 🔴 **同时暴露一条原文未预见的风险**:WS2812 **停更即保持最后颜色**,没有硬件"灭"。⇒ 上一版"`KILL` = 灭、与崩溃外观一致"的说法**必须补一句**:那个"灭"是**固件显式写出来的**,不是默认态;且**绝不能**把"灯灭"当作"不会发射"的证据(唯一证据是 `RF_KILL` 硬件门控)。详见 §2.4 与硬件文档 §2.7。

### 2.4 端口选择:控制通道走**原生 USB**(而不是板载 CH343)

**2026-09-21 二次核实**:本板(YD-ESP32-S3)有**两个物理 Type-C 口** —— 一个直连 ESP32-S3 原生 USB,一个经 **CH343P** 桥接 UART0。控制通道选定**原生 USB**:

| 判据 | 原生 USB | CH343 |
|---|---|---|
| 与手头这块板的关系 | **就是 ESP32-S3 自己** | 是桥接芯片,**手机看到的是 WCH 芯片,不是设备** |
| 额外器件 | **0** | 每台产品多一颗 CH343P |
| 占用 UART0(GPIO43/44) | **不占**(可留作调试) | **占用** |
| 能否 JTAG 调试 | ✅ 保留 | ❌ 该端口无 JTAG |
| WebUSB 视角 | Espressif VID `0x303a` | WCH VID `0x1a86` |

> ⚠️ **本 ADR 上一版在此处有一处事实错误,已更正**:它写"这块板在**同一个 Type-C 口**下枚举出两个 USB 设备(板载 **CH334 HUB**)"。那是**另一块 Waveshare 板**的事实 —— 本板**没有 HUB**,是**两个独立物理口**。**判据表与结论不受影响**(甚至更简单:用户插错口即可,不需要面对"一个口两个设备"的选择框)。详见 **F-4d-0** 的错因分析。
>
> ⚠️ **本项未经用户逐条确认**(提问时未选)。因此**记为"按上述判据选定,可复议"**,而不是"用户已定"。理由是新证据在提问之后才取得,而该证据**单向支持原生 USB**;同时两条路都仍是 USB,§2.1/§2.2 的结论不因这一项而变。**复议触发条件见 §6-3。**

## 4. ⚠️ 本 ADR 引入的**新风险**:控制通道从"多通道冗余"塌缩为**单点**

这是本决策**最重要、最容易漏掉**的后果,必须显式登记:

**取消 BLE 与 Wi-Fi 之前**,R-01(2.4GHz 自扰压掉无线)的失效模式是"**无线断了,但 USB 还在**"—— USB 是一条**保底**通道。
**取消之后**,USB 不再是保底路径,而是**唯一路径**。于是:

> **一旦 USB 通道不可用,设备就完全无法被指挥 —— 包括"中止发射"这条安全动作。**

由此产生一条**升级**:原本 **R-13**(PWA 能否经 WebUSB 访问 CDC-ACM 设备)的影响是"失去保底通道";现在它的影响是"**失去全部控制能力与全部配对能力**"。

| ID | 项 | 本 ADR 前 | 本 ADR 后 |
|---|---|---|---|
| **R-13** | WebUSB 可否访问该 CDC 设备 | 高(失去保底) | **阻塞级(失去唯一通道)** |
| **A-07** | "2.4GHz 发射中可经 USB 中止" | USB 是保底 | USB 是**唯一**手段 ⇒ **该判据的失败没有替代方案** |

**处置(已写入下游文档)**:

1. **TC-074a(WebUSB 实测)从"第一项实测"升为发布门禁**:它不通过则本批**没有可用的控制路径**。
2. **降级路径明确且唯一**:原生 Android USB Host 小壳(ADR-0003 §6)。⚠️ **不是**"退回无码 BLE 配对" —— 那会让防中间人机制名存实亡(契约 §7.1(1))。
3. **"断连即停发"的兜底实现不得依赖链路本身**(固件 §9):本批链路只剩一条,若该实现写成"等链路事件",则链路一断它也随之失效。**必须**是独立的时间戳 + 轮询。

## 6. 复议触发条件

1. **用户决定把 BLE 或 Wi-Fi 纳入后续批次** —— 届时本 ADR §2.2 保证的能力定义可直接接续,无需重推导
2. **TC-074a 不通过** —— 触发 ADR-0003 §6 的降级路径(原生 Android USB Host 小壳),**而不是**恢复 BLE 配对
3. **用户澄清控制通道应走板载 CH343** —— 只需改 §2.3 与固件初始化路径;`§2.1/§2.2/§4` 全部不变
4. **实测发现 USB 在某种合法操作序列下必然中断**(如模块插拔、供电切换)——需重新评估"单点通道"是否可接受,或提前把 BLE 拉回本批作为第二通道
