# ADR-0002:DeepSeek 智能分析放在手机 App 侧,设备只回传特征

- 状态:`accepted`(已由用户决策确认)
- 日期:2026-09-20
- 决策者:用户
- 影响面:协议契约 §3.6、§7;App 架构;固件内存与网络安全边界

---

## 1. 背景与问题

需求 F-09/F-10 要求:App 把捕获的信号特征发给 DeepSeek,得到信号类型/协议/威胁等级,并可据此下发动作指令。

需要决定:**谁去调用 DeepSeek?** 两个候选:

- **方案 A**:手机 App 调用,设备只回传原始特征
- **方案 B**:设备(ESP32-S3)直连 DeepSeek HTTP API,手机只展示结果
- **方案 C**:两者可切换

## 2. 方案对比

| 维度 | A:App 侧调用 | B:设备直连 | C:可切换 |
|---|---|---|---|
| API Key 存放 | 只在手机 | **必须存在设备 Flash** | 两处都要 |
| Key 泄露面 | App 本地,可加密存储 | 设备被物理获取即泄露;串口/OTA 都可能泄 | 最大 |
| TLS 内存开销 | 浏览器/原生承担 | ESP32-S3 上 TLS 握手约需数十 KB 堆,与 Wi-Fi + 射频缓冲争内存 | — |
| 换模型/换提示词 | 改 App 即可,免刷固件 | 每次都要刷固件 | 复杂 |
| 无手机时能否分析 | ❌ 不能 | ✅ 能 | ✅ |
| 离线场景 | App 可做本地规则兜底 | 设备不能兜底 | — |
| 审计与合规 | 集中在 App,一处告知用户 | 分散,设备侧难做用户同意流程 | 分散 |
| 复杂度 | 低 | 中高(证书、重试、内存) | 高(两套配置与密钥管理) |
| 流量成本 | App 有网即可 | 设备需自备网络出口(现场路由器不可控) | — |

### 决定性因素

1. **现场网络不可控**:场景 S1 是"设备接入现场路由器"。现场网络能否出公网、能否访问 `api.deepseek.com`,不由我们决定。把分析能力绑在现场网络上很脆弱。
2. **手机一定有网**:人在远处用手机遥控,手机通常具备蜂窝网络,是更可靠的分析出口。
3. **密钥最小暴露**:设备会被放在车内/背包,存在被物理接触的风险。设备不存 Key,泄露面直接归零。
4. **内存预算要留给射频**:ESP32-S3 的 RAM 要服务于 RMT 捕获缓冲、Wi-Fi/BLE 协议栈双跑。TLS 客户端是额外且非核心的负担。

## 3. 决策

**采用方案 A:AI 分析在手机 App 侧调用 DeepSeek;设备只负责特征提取与回传。**

设备对 AI 的职责边界:

- ✅ 从跳变序列提取 `features`(协议契约 §3.6):频率、调制、符号率、脉宽直方图、编码猜测、重复周期、帧位数、噪声底
- ✅ 按需回传原始 RLE 码流(供 App 本地保存或用户手动导出)
- ❌ 不发起任何 AI 网络请求
- ❌ 不存储任何 API Key 或第三方凭据
- ❌ 不因 AI 结论**自动**发射(见下)

## 4. 关键约束与后果

### 4.1 特征必须自包含

因为设备不参与 AI 交互,它无法"按需追问"。所以设备提取的 `features` 必须一次性包含模型判断所需的一切。若 AI 需要额外信息(例如更长的捕获、另一频点对照),必须由 App **发起第二次捕获**。

**后果**:`features` 的字段设计要以"回答『这是什么信号、有没有威胁』"为判据,而不是以"容易算"为判据。

### 4.2 特征哈希去重

同一信号会被反复扫到。App 侧应对 `features` 做规范化哈希,命中缓存则直接复用分析结果,避免重复计费。规范化的关键:排除时间戳、RSSI 抖动等不影响语义的字段。

### 4.3 AI 结论不得自动触发发射

即使威胁等级为 `high`,也不允许 App 自动发射。必须:

1. AI 给出 `recommended_actions[]` 作为**建议**
2. 用户在 UI 上确认
3. App 计算短时 HMAC 令牌(30s 有效)
4. 设备校验令牌 + 频段白名单 + 功率上限(协议契约 §3.7、§7)

**理由**:把"AI 判定"与"物理发射"直接连起来是危险的——模型会出错,而射频发射有法律后果。人工确认是这条链路上不可删除的一环。

### 4.4 上传内容边界

只上传以下内容给 DeepSeek:

| 上传 | 不上传 |
|---|---|
| 频率、调制、符号率、脉宽统计 | 原始 RLE 码流(除非用户显式勾选导出) |
| 编码猜测、帧结构推断 | 设备 ID、Wi-Fi SSID、设备地理位置 |
| 噪声底、RSSI | 任何能定位到具体场所的信息 |

需在 UI 上明确告知"本次分析将向第三方发送哪些字段"。

### 4.5 离线降级

无网络时 App 必须能降级:

- 本地规则库(按频率 + 调制 + 符号率做粗分类)给出初步判断
- 明确标注"离线结果,置信度低",并提示联网后可重新分析

## 5. 被否决的方案及理由

| 方案 | 否决理由 |
|---|---|
| B:设备直连 | 密钥物理暴露 + TLS 内存开销 + 现场网络不可控 + 换模型要刷固件。其唯一优势"无手机也能分析"与产品定位冲突——本产品**就是**由手机 App 控制的工具 |
| C:可切换 | 直接继承 B 的全部缺点,再叠加"两套密钥管理"。收益(灵活性)不抵成本 |

> 若未来出现"设备完全脱机自主监测"的产品形态,方案 B 应重新评估。届时建议把 AI 能力放在一个**独立的网关进程**里(而非 ESP32 上),而不是把 Key 塞进设备。
