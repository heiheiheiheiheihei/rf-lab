# ADR-003 · 码库模型与 RAW 脉冲存储

状态:**接受(0.8.0)** · 2026-11-24 · 决策者:项目负责人
相关:[ADR-001](ADR-001-radio-hal.md)、[`../00-mvp.md`](../00-mvp.md) §13、[`../01-ui.md`](../01-ui.md) §5.4、
[`../04-ref-mynova.md`](../04-ref-mynova.md) §5、[`../02-plan.md`](../02-plan.md) §5.3

> 结论:**0.8.0 不动码库、不动分区表。** CC1101 的原始脉冲是「会话对象」,只活在 RAM,
> 由浏览器导入/导出 `.sub`;协议型条目与 `.sub` 导入触发 v3,时间点在 0.8.x。

## 1. 背景

- 码库 v2:64 条 × **57B** = 3.7KB blob;`codes2`(magic `R3`,ver 2)与 v1 `codes` 并存;
  `id` 是位置号,`ERASE` 后前移;`LIST` 只输出 `id band code`([`../00-mvp.md`](../00-mvp.md) §13)。
- NVS 分区 **24KB**(0x6000),同时放 Wi-Fi/BLE PIN;没有文件系统,码库不能乱扩。
- 上游的一条 RAW 上限是 16,384 段 × 4B = **64KB**;本仓库首版取 4,096 段(16KB)。上游的教训是「NVS 只留元数据,
  脉冲进文件」,且它为此上了 TF 卡([`../04-ref-mynova.md`](../04-ref-mynova.md) §5)。
- 硬约束:分区表受 `check_partitions.py`/`flash.sh` 保护;NVS 不擦;`LIST` 不得让旧客户端解析错位。

## 2. 决策

### 2.1 0.8.0:码库零改动

- `codebook_rec_t`、`codes2`、`CODEBOOK_VERSION=2` **都不动**;不新增字段、不做 v3 迁移。
- CC1101 RAW 不进入码库:`SEND <id>` 仍只对固定码;RAW 走会话命令(§2.2)。
- 分区表不动,不新增 LittleFS/数据分区;NVS 布局不动。

理由:0.8.0 的 CC1101 只承诺原始 RX/TX,没有「协议条目」可存;为一个尚未存在的记录类型
提前改 blob,会把迁移风险提前,却没有收益。

### 2.2 RAW = 会话对象(RAM + 浏览器)

| 项 | 规则 |
|---|---|
| 缓冲 | `raw_session.pulses[4096]`(有符号 µs,16KB 内部 RAM);满了置 `full` 并停止,不静默截断 |
| 生命周期 | 上电/重启清空;新录制覆盖旧的;不写 NVS、不写 Flash |
| 采集 | `raw_start(cfg)` → `raw_read()` → 会话;浏览器经既有 SSE 看 `edges/full`(不新增轮询) |
| 发送 | 会话可直接 `tx_raw`(最多 4096 段,见 ADR-001);**不需要先保存** |
| 导入 | `POST /api/rf/raw` 上传 `.sub` 文本 → 解析 → 覆盖会话(不落盘) |
| 导出 | `GET /api/rf/raw` 返回当前会话的 `.sub` RAW 文本;浏览器负责存文件 |
| 并发 | 采集/发送互斥;被 Web/BLE/串口任一方占用时,其余入口得到 `owned=true` 并展示「占用中」 |

**关键判断**:本仓库是实验室工具,典型操作是「录一次 → 看时序/RSSI → 发一次 → 导出」;
浏览器天然是文件系统,设备只做解析/回放。这样省掉一次分区变更、一类掉电损坏面、
以及 NVS 的擦写寿命问题。

**避免的误修**:

- ❌ 把 raw 塞进 NVS blob:64KB/条,24KB 分区直接爆;且每次录制都在擦同一块。
- ❌ 为了 raw 顺手加 LittleFS:分区表要动,首次迁移必须 USB 重烧,
  还会破坏「UI 嵌在 app 分区、烧录即一致」这条 0.7.x 的简化。
- ❌ 把 raw 记成「第 65 条码」:`id` 位置语义、`SEND <id>`、UI 列表全会被污染。

### 2.3 v3:触发条件与预留形状(0.8.x,不实现)

**触发条件**(满足任一):CC1101 协议解码落地;`.sub` Key File 导入落地。

**形状**(只追加,不改 id 语义):

```text
v3 record = v2 record(57B) + kind(1) + freq_hz(4) + preset(1) + bits(1) + te(2) + key(8) = 74B
64 × 74 = 4,736B;blob 4,740B(≈4.7KB)
```

| 字段 | 含义 |
|---|---|
| `kind` | `0` = 固定码(YS),`1` = 协议型(CC1101/`.sub` Key) |
| `freq_hz` | 协议型频点;固定码为 0 |
| `preset` | 0..3([`../04-ref-mynova.md`](../04-ref-mynova.md) §4.2) |
| `bits` | 1..64 |
| `te` | 0 = 用协议默认 |
| `key` | 8 字节大端(与 `.sub` 一致) |

- **序列化定长、显式字节序,不用 `sizeof(struct)`**;magic `R4`、ver 3、key `codes3`。
- 读取顺序 `codes3 → codes2 → codes`;写 v3 成功后**保留** v2/v1 作为回滚快照(与现有策略一致),
  它们不随 v3 更新,不能当镜像。
- 迁移时 v2(3.7KB)+ v3(4.7KB)同时在 NVS 里,共 8.4KB,24KB 分区可容纳;迁移后仍要留
  Wi-Fi/BLE key 余量。
- **身份/去重**:固定码 = `band + code[0..2]`(现状);协议型 = `freq_hz + preset + bits + key`。
  两类之间**不互相判重**。
- **`LIST`**:固定码行保持逐字节不变;协议型行追加为新格式,例如
  ` 7  433.92M CAME 0012AB34`;`LIST LONG` 增加 `kind=`。旧客户端遇到不认识的行必须跳过,
  回归测试以「只有固定码的码库 → `LIST` 逐字节一致」为准。
- **写入路径**:`NEW/EDIT` 仍只建固定码;协议型条目只由「学习/导入」产生,`EDIT` 只允许改名/分组/符号,
  不允许改 `freq/preset/bits/key`(要改就重学,避免半改状态)。
- **API**:`/api/codes` 对固定码保持现有字段,新增 `kind`;协议型增加 `freq/preset/bits/key/te`。
  字段只增不删,旧 APP 忽略未知字段。

### 2.4 明确不做

- 不做统一槽位编码 `0=空 / 1..100=RF / 101..200=IR`(单一射频域,无收益)。
- 不做 raw 的 NVS/文件持久化;不做每槽 `.sub` 边车。
- 不做「协议型 → 固定码」自动降级(位时序推不出模块的 4B 语义)。
- 不改 `id` 位置语义,不做排序/重编号。

## 3. 后果

| 面 | 影响 |
|---|---|
| 正面 | 0.8.0 无迁移风险;无分区变更;raw 不磨损 Flash |
| 负面 | 重启后 raw 丢失;要保存必须导出到浏览器 |
| 风险 | 浏览器上传/下载要新增文件读写路径,需要大小上限与超时(见 §5) |
| 风险 | v3 的 `LIST` 扩展会影响 TUI 与外部脚本;0.8.x 必须同步客户端并加回归 |

## 4. 验收

- **0.8.0**:码库 v2 主机测试与真机 `LIST` 零变化;`INFO` 的 `stored=` 与容量不变;
  raw 会话不产生任何 NVS 写入(可用 `nvs_get_stats` 或擦写计数证明)。
- **0.8.x(v3)**:v2→v3 迁移逐字节回滚测试;现有固定码 `LIST` 逐字节一致;
  `.sub` Key 导入 → 导出 round-trip;协议型发送与原始时序一致;NVS blob ≤5KB。
- **上限**:上传 `.sub` ≤64KB(4096 段 × 16B 文本量级),超限返回 413;解析拒绝
  `count > 4096`、`|us| > 1,000,000`、非数字/坏行。

## 5. 重访条件

- 出现「离线带码出门」的真实需求,或现场无法带浏览器:另写 ADR 评估数据分区
  (需 USB 重烧、改 `check_partitions.py`/`flash.sh`),不要在本 ADR 上打补丁。
- 协议解码只做 1–2 个协议时,可先不扩 v3,用「导入即发、不保存」的最短路径;
  v3 等确有「存下来复用」的需求再落。
