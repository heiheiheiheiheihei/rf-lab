## 1. 验证层次

| 层 | 名称 | 环境 | 能验证什么 | **不能**验证什么 | 自动化 |
|---|---|---|---|---|---|
| **L0** | 单元测试(PC 纯逻辑) | 开发机,无任何射频硬件 | 协议帧编解码、分片/重组、RLE 编解码、特征提取、令牌校验、频段门禁与功率夹取、状态机迁移、限流器、审计记录格式化 | 任何真实射频行为;真实时序抖动 | ✅ CI 全自动 |
| **L1** | 集成测试(PC,双实例/模拟器) | 开发机,以模拟 RF 后端驱动完整应用逻辑 | App↔设备全消息流、错误码路径、断线重连、超时、限流与抢占、能力集协商 | 真实 SPI/RMT 时序、功耗、中断延迟 | ✅ CI 全自动 |
| **L2** | 硬件在环(HIL) | 真实设备 + 假负载/屏蔽箱,PC 作上位机 | 模块驱动、SPI 通信、RMT 采集、看门狗与复位恢复、真实发射时序与功率档位、审计掉电保持 | 空口传播特性、绝对辐射功率(受测试夹具影响) | ⚠️ 可脚本化,但硬件独占,须串行 |
| **L3** | 空口验证 | 真实设备 + 频谱仪/SDR + 天线 | 频率准确度、占用带宽、杂散发射、占空比、辐射功率、屏蔽泄漏 | 端到端用户价值 | ❌ 人工 |
| **L4** | 现场验收 | 真实场景 + 手机 + 被测网络 | A-01..A-07 全部成功判据 | — | ❌ 人工 |

### 1.1 为什么逻辑层**必须**能在 PC 上测

这不是"nice to have",而是这个项目的结构性要求:

1. **射频硬件是稀缺资源且不可并行**。三个模块共用一个设备,一次只能跑一个测试;多模块并发会互相干扰(产品定义 C-02:每模块独占 SPI 与天线)。若把协议与算法测试绑在硬件上,回归一次就要独占设备数十分钟,CI 根本跑不起来。
2. **合规门禁逻辑必须每次提交都跑**,不能靠人工抽查。`tx_whitelist` 判定、功率夹取、令牌校验这类代码一旦被改坏,后果是**设备真的会在禁发频段发射**——这是本项目最高等级的风险,值得拥有最密集的自动化覆盖。而这类逻辑**本质上与硬件无关**。
3. **协议契约是权威来源,也是最容易漂移的东西**。契约 §8 规定"新增消息类型/字段不升 `VER`",这意味着兼容性靠**契约测试**而非版本号守护。契约测试只能在 PC 上跑。
4. **A-04(DeepSeek 链路)与 L0/L1 完全解耦**,可以在没有设备的情况下先完成。
5. **开发者不在硬件旁边是常态**。README 明确本阶段无固件实现、无 ESP-IDF 独立安装;设计阶段的算法验证必须能在纯 PC 环境完成。

## 2. 可测性要求(对固件架构的输入)

以下要求应写入固件架构文档,它们是本验证计划能否落地的前提。**违反其中任一条,都会导致对应层的测试无法自动化**。

| # | 要求 | 理由 / 违反的后果 |
|---|---|---|
| T-01 | **协议编解码、分片重组、RLE 编解码、特征提取、令牌校验、频段门禁、功率夹取,全部实现为不依赖硬件的纯函数**:不 `#include` 任何 `esp_*.h` / FreeRTOS 头,只依赖 `stdint.h` / `stdbool.h` / `string.h` | 这些是 L0 的全部内容。一旦混入 `ESP_LOGx` 或 `esp_timer`,PC 上就编译不过,CI 覆盖直接归零 |
| T-02 | **单一实现,不打桩复制**:PC 测试与固件编译**同一批源文件**(如 `firmware/components/rfcore/`),通过构建系统切换编译目标,**不允许**维护一份"给测试用的副本" | 否则会出现"测试全绿但固件是另一份代码",这是最昂贵的假信心 |
| T-03 | **RF 访问藏在可替换接口之后**:定义 `rf_hal_t`(`probe` / `tune` / `tx` / `idle` / `read_rssi` / `read_edges`),生产实现走 SPI/RMT,测试实现为模拟器。**模拟器必须记录每一次 `tx()` 调用**(时间、频率、功率、时长) | §6 的合规负向测试要求断言"发射调用次数 = 0";没有这个记录口就无法证明拒绝是真的 |
| T-04 | **时间源可注入**:所有超时、令牌有效期、限流窗口、占空比统计都通过 `now_ms()` 取值,测试可注入假时钟 | 分片超时 500ms、令牌 30s、限流 50msg/s 若直接调 `esp_timer_get_time()`,测试只能靠 `sleep`,既慢又不确定 |
| T-05 | **确定性**:同输入必同输出。核心路径禁止 `rand()`;必须的随机(如令牌 nonce)从注入的熵源获取 | 保证失败可复现。非确定性的测试结果等于没有测试 |
| T-06 | **拒绝路径必须可枚举**:每一处拒绝都返回 §6 中明确的 `code`,**不允许静默失败、不允许用兜底值继续执行** | "静默失败"在合规门禁上是致命的——它会让一个越界请求看起来成功了 |
| T-07 | **审计记录是结构化数据,不是 `printf`**:每条记录以结构体/可序列化对象产出,写入环形日志前可被测试直接断言 | TC-029/TC-030 需要逐字段断言,解析日志文本既脆弱又不可靠 |
| T-08 | **法定常量表独立成头文件**并与运行时可写配置分离:法定频段边界、功率上限、占空比上限以 `const` 编译进去 | 合规文档 §4.4 的"编译期常量层"。测试可直接断言每个频段的限值,并在常量被误改时失败 |
| T-09 | **能力集 `CAPS` 由运行时真实探测生成**,不得硬编码模块列表 | 否则 `module_absent` 场景无法构造,TC-005 会变成假测试 |
| T-10 | **看门狗与复位原因可观测**:开机后能读到上次复位原因(正常/看门狗/异常) | TC-053 需要区分"看门狗复位"与"上电复位",否则无法证明看门狗真的起作用 |
| T-11 | **承载上限是运行时数据,不是编译期常量**:`CAPS.limits.ble_frame_max` 由设备按**实际协商的 ATT 载荷**算出并上报;分片/组帧逻辑从该值取上限,不硬编码 3669 或 4096。`DATA_CHUNK` 的分块大小同样按承载自适应 | 契约 v1.1 §2.2.1:3669 是**上界不是目标**,实际 ATT 载荷由协商决定,协商越小可重组整帧越短。硬编码会让换一台手机就静默失败。TC-024b/TC-024c 只能在此设计下才可测 |
| T-12 | **扫描命中缓存与 `scan_id` 可观测**:设备为每次扫描分配 `scan_id`,命中缓存在设备端保留到下一次扫描开始;缓存可被测试代码取长度与内容 | TC-034a/TC-034b 需要断言"分页取回的总条数 == `hits_total`",没有可观测的缓存就无法区分"设备丢了"与"推送被限流了" |
| T-13 | **特征提取的三级不确定性是真算出来的,不是填默认值**:`*_confidence` 必须由算法依据证据强弱产出;证据不足时 `*_guess` 字段置 `null` 而非低置信度的胡猜;`raw_semantics` 镜像 §3.5 的 `FLAGS` bit1;`incomplete` 由 `truncated` / 丢帧传播 | 契约 v1.1 §3.6。固件文档 §"F-Q5/F-Q6 的实现义务"明确警告:若固件只填默认值,契约的不确定性表达就落空,AI 仍会把猜测当事实。TC-034c/TC-034d 是这条要求的验收形式 |
| T-14 | **"静默截断"在代码层面不可达**:超承载上限的帧走 `frame_too_large` 拒绝分支;`max_edges` 超限走钳制分支并置 `truncated`;限流丢弃走计数分支并回 `throttled`。**三处都不得存在"截断后继续"的路径** | 契约 v1.1 §2.2.1/§3.3/§3.4 三处明令;合规文档红线 R10。一个"截断后继续"的分支会让下游把残缺数据当完整信号——这是本项目最隐蔽的失效模式 |
| T-15 | **M3 发射与控制链路的时分互斥可观测**:测试可读到"M3 静默窗口"的申请/释放事件、窗口时长、以及窗口内被延迟的控制帧数 | TC-099/TC-100 与硬件文档 R-01 的需要。没有这个可观测点,"发射前先申请静默窗口"就无法验证是否真的实现 |

### 3.11 契约 v1.1 新增判据:门 3(显式用户确认)= 两段式发射 `armed`

契约 v1.1 §7.1(4) 明确门禁有四道,`auth_token` 只是**第四道**;前三道是频段白名单、功率上限、**显式用户确认**。v1.1 §3.7 把"显式用户确认"从抽象原则**具化为两段式发射**:

1. 第一阶段:`TX_REQUEST` 带完整参数 + 令牌;门禁**全部通过**后设备回 `TX_STATUS{state:"armed"}` —— 此时**尚未开始辐射**;
2. 第二阶段:App 在 `CAPS.limits.arm_timeout_ms`(示例 5000ms)内发第二次 `TX_REQUEST`,**只带** `{armed_ack:true}`;
3. 超时未收到二次确认 → 自动回落 idle,回 `TX_STATUS{state:"failed", code:"arm_timeout"}`。

门 1(白名单)由 TC-035..TC-038 覆盖、门 2(功率)由 TC-039/TC-040 覆盖、门 4(令牌)由 TC-041..TC-044 与 TC-043a 覆盖;**门 3 由本节覆盖**。

### 4.1 A-05 的"双条件"要求

A-05 的证据必须**同时**包含:

1. **协议层**:`TX_STATUS{state:"denied", code:<明确错误码>}`;
2. **RF 层**:`rf_hal.tx()` 调用计数 = 0(L0/L1),或功率计读数 = 底噪(L2)。

只有第 1 条不构成通过。原因很直接:一个错误码证明的是"代码走到了拒绝分支",而不是"射频前端没有发射"。两者之间的差距正是本项目最需要验证的地方。

### 4.2 A-02 的具体比对方法

**参考源优先级**(从高到低):

1. **射频信号发生器**(首选)。输出已知频率的连续波,频率准确度可直接溯源,是唯一能给出**绝对**频率基准的手段。
2. **已知遥控器**(次选)。**注意:必须用频谱仪实测其频点作为参考值,不得使用标称值(如"433.92MHz")**——廉价遥控器的晶振偏差可达 ±100kHz 量级,正好是本判据的门限宽度。用标称值做参考会得到虚假的通过。
3. **RTL-SDR / HackRF 作为参照接收机**(仅作交叉验证)。廉价 SDR 的晶振偏差可达 ±20ppm 以上(433.92MHz 上即 ±8.7kHz,尚可接受;但温漂与频偏校准不可忽略),**必须先用电台/信号源标定后使用,且只能用于相对比较,不能作为绝对基准**。

**测量布置**(避免近场耦合误差):

| 项 | 要求 | 理由 |
|---|---|---|
| 距离 | DUT 与参考天线间距 **≥3m**;并做 1m / 3m / 10m 三点测量 | <1m 时处于近场,读数虚高且可能出现频率牵引;三点测量用于**验证远场条件成立** |
| 场地 | 开阔场,或吸波环境 | 反射会造成多径导致的频率读数抖动 |
| 极化 | 参考天线与 DUT 天线**同极化**,尽量等高 | 交叉极化会引入额外衰减,恶化信噪比 |
| 时序 | 参考源与 DUT **交替发射**,绝不同时 | 同时发射会互相压制,无法分辨 |
| 预热 | DUT 上电预热 ≥10 分钟再测 | 晶振温漂在冷启动后数分钟内最显著 |
| 重复 | 每个频点,DUT 读数与参考读数**各取 3 次的中位数** | 抑制单次抖动 |
| 记录 | 环境温度、DUT 上电时长、距上次频率校准的时间 | 用于解释偏差来源 |

**A-02 记录表字段**:

| DUT 模块 | 设定频率 | DUT 读数(中位数) | DUT 偏差 | 参考读数(中位数) | 参考偏差 | **DUT − 参考** | 判据 ±100kHz | 结论 |
|---|---|---|---|---|---|---|---|---|

**偏差归因规则**(比"是否通过"更有价值):

- 若 DUT − 参考是一个**近似恒定的偏移** → 属于**晶振校准**问题,不是扫描算法问题。修法是晶振校准或软件频偏补偿。
- 若偏差**随频率线性增长** → 属于参考时钟的频率误差(ppm 级),同样指向晶振。
- 若出现**离散跳变**或**与步进相关的周期性误差** → 属于**调谐计算/步进量化**问题(例如把 `f_hz` 换算寄存器值时整数截断)。
- **两个模块必须分别给结论**:CC1101 与 SI4463 的参考晶振与步进算法不同,一个模块通过不能代表另一个。

### 4.3 A-06 的验收方法(带外必须"可见地失败")

**为什么单独给 A-06 立一条判据**:按 ADR-0001 §5.1,硬件**已定稿为三模块、不增补**,覆盖永久停在 387–525MHz。而用户最可能去试的几个频点(315MHz 遥控器、868/915MHz 传感器)**恰好全部落在空白里**。此时唯一能防止"用户以为没信号、其实设备听不见"的,就是**让失败可见**。这是本决策下**最容易在实现中被做成静默成功**的一环,因此必须有独立判据。

**A-07(2026-09-20 新增判据)**:2.4GHz 发射期间控制通道不中断,已在 §3.8 展开为 **TC-074g / TC-074h**。

> **为什么单独给 A-07 立一条判据**:R-01 是**架构前提级风险**——M3 的 20dBm PA 与主控 2.4GHz 天线同壳体、厘米级间距,**发射时本机 Wi-Fi/BLE 基本必然被压掉**。后果不是"掉线",而是**设备自己发出的发射动作自己收不到中止指令**。屏蔽室**只挡内外互扰,挡不住这个自扰**。因此 USB 有线通道(F-11/ADR-0003)从"便利功能"升级为**安全相关的必要能力**,并且**必须有实测证据**——不接受"按设计应该不会断"这种推断。
>
> 该判据的第二个落点是**诚实呈现**:无线通道确实会被压掉,但 App **必须说明原因**,不得渲染成"设备离线"。否则用户会去排查一个并不存在的问题,而真正的原因(自己正在发射)被掩盖。这与 A-06 的"可见地失败"是同一类要求:**不要把"我不知道/我做不到"伪装成"一切正常"。**

**测试频点(按"用户最可能误试"排序)**:

| 频点 | 属于哪个空白 | 用户为什么会试 |
|---|---|---|
| **315MHz** | 119–300 | 国内大量廉价遥控器/车库门用 315MHz |
| **868MHz** | 525–779 | 欧洲 ISM 常识频段,传感器常见 |
| **915MHz** | 928–1050 | 北美 ISM 常识频段 |

**判定"可见地失败"的三个必要条件(缺一不可)**:

1. **协议层**:`START_SCAN` 返回 `ERROR{band_out_of_range}`(完全带外)或 `WARN{band_clipped}`(部分带外);`SCAN_DONE.coverage` 为空或仅含真实可扫区间。
2. **不得静默成功**:响应**不得**是"正常完成 + `hits_total == 0`"这种形态。`hits_total == 0` 只有在**请求范围确有覆盖**时才是合法结果。
3. **界面层**:App 必须把"超出本机能力"与"该频段无信号"**在视觉上区分开**。二者语义完全不同(前者是设备缺陷,后者是环境结论),混同即为不通过。

**反例(明确判为不通过)**:

| 反例 | 为什么不可接受 |
|---|---|
| 设备回 `SCAN_DONE{hits_total:0, coverage:[{315e6,315e6}], aborted:false}` | `coverage` 谎报了从未扫过的区间 —— **这正是 ADR-0001 方案 D 被拒绝的理由** |
| 设备回 `WARN{band_clipped}`,但 App 只把 warning 写进日志、界面照常显示"未发现信号" | 用户看不到,等于静默 |
| 扫频范围选择器允许把 315MHz 拖进选择区并点击"开始" | 界面在**引导**用户进入一个不可能成功的路径;应由 `CAPS` 驱动禁用或标注 |

**证据形式**:三个频点的**协议帧日志 + App 界面截图(需能看出提示文案)+ 扫频选择器的能力边界截图**。

## 5. 扫频准确性验证的补充说明

- **为什么不能用"扫到自家遥控器就算对"**:遥控器的实际频点未知,用未知量验证未知量不构成验证。必须有至少一个已知量(信号发生器或频谱仪实测值)。
- **RSSI 是相对量,不是功率计**。产品定义 §3.1 已明确"不做发射功率的精确标定(仅档位控制)"与"不做通用频谱分析仪(无扫频前端/无校准功率测量)"。因此 **A-02 只验频率,不验幅度**;任何试图从 RSSI 反推绝对功率的做法都不在本项目的验证范围内。
- **扫描速度与准确性的关系必须记录**:`dwell_ms` 越短,检测概率越低。A-02 应在**约定的 `dwell_ms` 下**进行并在报告中写明该参数——脱离驻留时间谈扫频准确性没有意义。

## 6. 合规负向测试

见 §3.7 的 TC-060..TC-066、§3.10 的 TC-043a/043b/043c/TC-093/093b/094、§3.11 的 TC-095..TC-098b、§3.12 的 TC-099..TC-101。本节说明**为什么这样设计**。

### 6.1 四类负向输入(按契约 v1.1 §7.1(4) 的四道门禁归类)

| 门 | 负向输入 | 期望错误码 | RF 侧证据 | 审计断言 |
|---|---|---|---|---|
| **门 1** 频段白名单 | 白名单为空(出厂态);或频率在白名单区间外 | `tx_denied` | 功率计 = 底噪;`tx()` = 0 | 记录含原因标识(白名单为空 / 频率不在白名单) |
| **门 2** 功率上限 | 超出 `tx_power_cap_dbm`、`tx_max_dbm` 或该频段法定限值 | `tx_denied` | 同上 | 记录**同时含请求功率与被允许的上限**,便于审计判断 |
| **门 3** 显式用户确认 | 未经用户显式确认的发射请求 | `tx_denied` | 同上 | 记录含 `user_confirmed:false` |
| **门 4** 有效令牌 | 无令牌 / 错令牌 / 过期 `seq` / 重放同 `seq` / 篡改参数后复用 / 跨设备令牌 | `tx_bad_token` | 同上 | 记录含 `auth_token_id` 与 `seq`(可追溯),**绝不含令牌明文** |

**另有一类不属四道门、但同属合规负向的输入**:

| 类别 | 负向输入 | 期望错误码 | 说明 |
|---|---|---|---|
| 模块能力边界 | 频率超出 `CAPS.modules[].bands` | `band_out_of_range` | 与门 1 是**两道独立判定**:模块能调到哪里 ≠ 法规允许发到哪里(合规文档 §4.1 的 P3 注释) |
| 芯片能力天然越界 | nRF24L01P 的 2484–2525MHz(RF_CH ≥ 84) | `tx_denied` | 不是"用户请求越界",而是"芯片能力超出法规"——最容易被遗漏的一类(TC-063) |
| 承载上限 | 帧 `LEN > ble_frame_max` | `frame_too_large` | 契约 §2.2.1;**禁止静默截断**(TC-024b) |
| 数据完整性 | 命中被限流丢弃却不告知 | `throttled` + `hits_dropped > 0` | 契约 §3.3;**禁止把 `hits_dropped > 0` 当正常结束而不告知**(TC-034a/TC-034b) |

### 6.2 补充要求

1. **所有负向拒绝必须在同一次测试会话中全部复现**,并使用**同一份固件二进制**(记录哈希),避免"分别在不同版本上验证过"的拼接式结论。
2. **拒绝后不得有副作用**:拒绝后设备应停留在原状态,不得留下"已 armed"的标志位,不得影响后续合法请求(TC-045 必须在 TC-035..TC-044 之后**立即**执行并成功)。
3. **2.4GHz 的 2483.5MHz 硬边界**(TC-063)是独立的负向用例,因为它不是"用户请求越界",而是"芯片能力天然越界"——这类风险最容易被遗漏。
4. **四道门必须逐一独立验证**:门 1 / 门 2 / 门 4 分别由 TC-035..TC-044 与 TC-043a/043b、TC-093 覆盖;门 3(显式用户确认)在 v1.1 中已具化为**两段式发射**——由 **TC-095 / TC-096 / TC-097 / TC-098 / TC-098b** 覆盖。这是契约 v1.1 §7.1(4) 的明文要求("任何一道不过即拒绝,且不因令牌有效而放宽")的验收形式。
5. **"静默截断"必须被证伪,而不只是被禁止**:对 TC-024b 的校验不能只看错误码,还要断言下游收到的数据长度**要么等于原始请求长度、要么明确失败**,不存在"变短了但没报错"的第三种结局(合规文档红线 R10)。

### 8.1 放行规则(建议,五条全部满足)

1. **S0 与 S1 数量为 0**;
2. **A-01..A-05 全部通过**,且 A-05 具备 RF 侧证据(§4.1 的双条件);

### 9.1 没有昂贵仪表时如何降级验证

**结论前置:合规相关的定量结论(功率、杂散、占用带宽、占空比)在没有频谱仪/功率计时无法验证。** 不得用 SDR 出具此类结论——SDR 的绝对幅度校准误差远大于合规判据的裕量,用它"证明合规"比不验证更危险。

可行的降级路径:

| 想验的东西 | 降级方案 | 是否可接受 |
|---|---|---|
| 合规门禁逻辑正确性 | 完全在 L0/L1 用模拟器验证(`tx()` 调用计数 = 0) | ✅ **完全可接受**,且这是主要手段 |
| 设备**确实**没发射 | 假负载 + 功率计;若无功率计,用**二极管检波探针 + 示波器**定性判断"有/无输出" | ⚠️ 定性可用,定量不可用 |
| 频率准确度 | 已知遥控器 + 频谱仪实测值 | ✅ 可接受(A-02 判据本身容忍此降级) |
| 发射功率 | **必须委托检测机构或租用频谱仪** | ❌ 不可降级 |
| 杂散发射 | 同上 | ❌ 不可降级 |
| 屏蔽泄漏 | 同上 | ❌ 不可降级 |
| 2.4GHz 是否越界 | 在 L0/L1 用门禁用例证明(TC-063) | ✅ 逻辑层可接受;但整机仍建议委托测试 |
