设备内自检的两层含义:

- `200 /api/hello` 与 `200 /api/state` 证明 HTTP 路由、JSON 响应、lwIP 回环/AP 路由可用;
- `200 /api/events` 证明 SSE 头 + 首帧 `hello` + `state` 真的发出来了;
- `202 /api/cmd` + 随后串口出现 `OK disp=test 1s` 证明 **POST → 队列 → main → 命令执行** 全链路,
  不是只回了一个 202。

OLED 开机页用 `DISP SHOW` 帧缓冲复核(不读玻璃;含 PIN 的原始帧缓冲日志已删除):

```text
# fb 72x40 '#'=on (screen content, not read back from glass)
... 可反解出 RF-Lab 0.6.0 / BLE PIN **** / 192.168.4.1
OK fb 72x40
```

## 4. 根因与关键判断

1. **1MB 分区表事故(已修)**
   - 现象:带 `WEBTEST` 的镜像 1,062,304B 烧录后反复 `RTC_SW_SYS_RST`,无 app 横幅。
   - 根因:`pio run -t upload` 只写 app;flash 里仍是默认 **1MB** app 分区
     (读 0x8000 得到 `factory size=0x100000`)。镜像跨过 1MB 后无法启动。
   - 修复:`board_build.partitions = partitions.csv`(PlatformIO 自己也会生成
     `partitions.bin`,不写这行会覆盖 sdkconfig 的自定义表);`tools/flash.sh` 一次写
     bootloader + 2MB 分区表 + app;`firmware/scripts/check_partitions.py` 在构建后
     解析 `partitions.bin` 并拒绝非 2MB。
   - 避免的误修:❌ 删掉 `WEBTEST`/缩功能把镜像压回 1MB —— 那是把布局问题伪装成功能问题;
     ❌ 直接 `erase_flash` —— 会丢 NVS 码库,而分区表/引导器写入并不需要擦 NVS。

2. **HTTP handler 上限**
   - 现象:首版启动打印 `web init failed: ESP_ERR_HTTPD_HANDLERS_FULL`。
   - 根因:IDF 默认 `max_uri_handlers=8`,注册了 9 条 URI。
   - 修复:`cfg.max_uri_handlers=12`;`max_open_sockets=5`(2 SSE + 3 短请求)。

3. **SSE 不能阻塞 httpd 主任务**
   - 采用 `httpd_req_async_handler_begin()` + 每连接独立任务;SSE 缓冲/上下文用 heap,
     不在任务间共享 static buffer。
   - 状态快照按序号推送;`state`/`codes` 由 main 侧缓存,避免 25Hz 长发心跳刷爆 BLE/SSE。

4. **单一业务逻辑**
   - Web/BLE/TUI 最终只提交 0.5.0 已验证的命令行;不在 C3 上复制 `F0/FE/FF` 时序。
   - 上机 `SEND` 851ms / `LONG` 224ms / `STOP` 51ms 与 0.5.0 的 0.85s / ~0.2s / ~0.02–0.05s 同量级。

5. **安全边界**
   - (历史基线)AP 常开 + WPA2;Wi-Fi 改成 STA-first/AP fallback 后见 [`2026-11-15-wifi.md`](2026-11-15-wifi.md)。BLE 只有应用层 4 位 PIN;Web 的 ARM 只是防误触。
   - 这三条都写进 `01-ui.md` 的代价表,没有把 PIN/ARM 说成硬门控。
