## 2. 复现

```bash
./tools/flash.sh /dev/ttyACM0
python3 tools/wifi_selftest.py --port /dev/ttyACM0 \
    --log docs/evidence/2026-11-15-wifi.log
```

脚本步骤(自动):

1. `WIFI CLEAR` → `INFO` 断言 `mode=ap ap_on=1`;
2. 配置不存在的 SSID → `INFO` 断言 `mode=apsta ap_on=1`;
3. 等待 18s → `INFO` 仍为 AP 可用,`WEBTEST` 经 AP 200;
4. 再写入错误凭据后 `RESET` → 启动串口断言 `mode=connecting ap_on=0`;
5. 等待 18s → 断言串口 `AP FALLBACK`、`mode=apsta ap_on=1`;
6. `WEBTEST` 200 → `WIFI CLEAR` → 断言 `mode=ap ap_on=1`.

## 4. 状态机与关键判断

```text
无凭据 ──────────────────────────────▶ ap
有凭据 ──启动 STA-only──成功──▶ sta(局域网 IP,AP 关)
                         └15s 失败──▶ apsta(AP 开 + 退避重连)
sta 掉线 ────────────────────────────▶ apsta(AP 立即开 + 退避重连)
ap/apsta 里配网 ──────────────────────▶ apsta(AP 保持,避免踢掉配网浏览器)
WIFI CLEAR ──────────────────────────▶ ap(删凭据,STA 停)
```

1. **为什么 STA-only 启动,而不是 APSTA 常开?**
   用户要求"连不上才回 AP";AP 常开会一直暴露 WPA2 热点,也增加空口占用。
   代价是失败时要等 15s 才能连 AP,这个等待写进 UI 的 `WIFI CONNECTING` 提示。

2. **为什么失败后是 `apsta` 而不是纯 `ap`?**
   回退后仍要后台重连(5/10/20/30/60s 退避);纯 AP 会停掉 STA,再次失败/恢复都要人工。
   AP 始终可用,所以"回退到 AP"的可用性成立。

3. **为什么 AP 里配网成功后不立刻关 AP?**
   关 AP 会踢掉正在提交配网的浏览器,用户看不到结果。配网成功保持 APSTA,
   下次启动才回到 STA-only;UI 显示 `LAN + AP`。

4. **避免的误修**
   - ❌ 让 AP 一直开着,只改状态字符串:没有真正回退,也违背"连上后 LAN 访问"的资源取舍。
   - ❌ 15s 超时后只打日志、不切模式:用户仍然连不上 AP。
   - ❌ 配网成功立刻 `esp_wifi_set_mode(WIFI_MODE_STA)`:会断正在配网的连接,还可能触发 STA 重连。
   - ❌ 失败后擦掉 NVS 凭据:用户下次还得重输;`WIFI CLEAR` 才是显式删除。
