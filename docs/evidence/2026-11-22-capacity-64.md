# 2026-11-22 码库容量上限:128 → 96 → 64,瓶颈在静态 RAM 不在 NVS

状态:`measured(主机 + 上机)` · **未发 RF**
提交:`c8e93d9 fix(sse): stream the codes snapshot instead of copying it`
设备:`/dev/ttyACM0` · 板 `RF-Lab-1B59` · 当前 `build=c8e93d9 / ui=d0824ba5`

## 1. 结论

| 容量 | JSON 缓冲 | 静态 RAM | 上机结果 |
|---|---|---|---|
| 32(原) | 6,144 B | 73,540 B(22.4%) | 正常 |
| 128 | 24,576 B | 150,772 B(46.0%) | ❌ `ble init failed: ESP_ERR_NO_MEM` + `web init failed: ESP_ERR_HTTPD_ALLOC_MEM` |
| 96 | 20,480 B | 131,188 B(40.0%) | ❌ 启动即复位循环(干净重建同样复现) |
| **64** | **12,288 B** | **88,692 B(27.1%)** | ✅ BLE/HTTP 正常,`heap free≈34.7KB`,自检 **26/0/1** |

**NVS 不是瓶颈**:24 KB 分区放 128 条(7.3 KB blob)也够,但 `/api/codes`、BLE 快照、
SSE 上下文各自复制一份 12–24 KB 的 JSON,把静态 RAM 和堆吃穿。
**64 是当前固定缓冲架构下可用的最大值**;再往上需要把 `/api/codes`、BLE 快照、
SSE 都改成流式/分页(见 §5)。

## 2. 两个内存修复(64 能跑起来的原因)

1. **BLE 码快照不再复制两份**([`ble_link.c`](../../firmware/src/ble_link.c)):
   `s_line` 从 12.4 KB 降到 1.7 KB,`s_codes` 里原地拼 `{"t":"codes",…"items":<json>}`
   (memmove),通知字节不变 → 静态 RAM **-10.6 KB**。
2. **SSE 直接流式发送只读快照**([`web_server.c`](../../firmware/src/web_server.c)):
   `sse_ctx_t` 去掉 12 KB 的 `codes` 副本(26 KB → ~4 KB),通过
   `app_lock_codes()` 分块发送 header / JSON / `}`;SSE 字节不变。
   否则 64 条时 `/api/events` 返回 `503 oom`(calloc 26 KB 失败)。

另外一个**迁移 bug**在第一次 128 上机时暴露:旧 v2 blob 固定 1,828 B(32 条),
容量改大后 `store_read_v2` 要求正好 7,300 B,设备报
`codebook v2 corrupt`,码库看似全丢。已修成「≥ header + count×57 即接受」,
并加了 32 条长度 blob 的回归测试(见提交 `618a57d`、`0050ef5`)。
