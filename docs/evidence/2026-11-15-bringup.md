## 1 控制台与模块在线

```
>>> INFO
# RF-Lab fw=0.4.0 (ESP32-C3 + YS-RF34DL)
# module UART1 9600 8N1 TX=GPIO3 RX=GPIO4
# console uart0:on usb:on 115200 8N1
OK stored=0/32 rx_bytes=0 frames=0 acks=0 dups=0 stray=0 resync=0

>>> MODE single          ACK 0xF2 OUTPUT_SINGLE_OK   (~0.10s)
>>> MODE continuous      ACK 0xF3 OUTPUT_CONT_OK     (~0.05s)
```

观察:端口打开后**第一次写入前读不到数据**(USB CDC 缓冲不主动刷新);写任意一行后历史输出才一起出来。不影响使用,但 `tools/rf34dl.py` 因此先写一个空行再读。

## 2 学码

按原遥控器 3 个键(模块距遥控器约 1m,天线已接):

```
LEARN id=2 band=315M code=5555033C
LEARN id=3 band=315M code=5555034B
RX id=3 band=315M code=5555034B
RX id=2 band=315M code=5555033C
RX id=1 band=315M code=5555034C
```

统计:`rx_bytes=138 frames=17 acks=2 dups=4 stray=0 resync=0`。
`138 = 17×8 + 2` 精确对账,说明解析没有错位、没有丢字节;`dups=4` 是按住键时的连发被 600ms 去重挡掉的。

## 3 发射

```
>>> SEND 1
ACK 0xF0 TX_OK            (~0.85s)
OK tx id=1 band=315M code=5555034C
```

15 次重复 `SEND 3`(间隔 2s):**15/15 全部 F0**。

第一次按 500ms 等应答时每次都打印 `WARN … no F0 within 500ms`,F0 随后才到 —— 属于窗口过短导致的**误报**,已把窗口改为 1500ms。

## 4 空中链路(关键证据)

1. 模块对准学习型遥控器,连续发 15 次 `5555034B`(315M)。
2. 学习遥控器**学到了**。
3. 再按学习遥控器,模块解出:

```
RX id=3 band=315M code=5555034B
```

→ 码值与发射值一致。这是「真的发射出去了」的直接证据,比 `F0`(UART 层应答)强一档。

## 5 波特率与恢复

```
>>> BAUD 57600     ACK 0xF1 BAUD_OK   (~0.10s)
>>> SEND 3         ACK 0xF0 TX_OK     (~0.85s)   ← 57600 下收发正常
>>> BAUD 9600      ACK 0xF1 BAUD_OK   (~0.15s)
>>> RECOVER        OK module baud=9600 (~0.15s)
```

教训:`F1` 落在**旧**波特率上、约 0.1s 才到。最初把切换前的等待设成 80ms 并 flush,结果每次都误报「no F1」——命令其实已生效。现已改成切换前等满 1500ms。

## 6 长发 / 停止

```
>>> LONG 3     (无 F0,1500ms 窗口内无任何字节)
>>> STOP 3     (无 F0)
>>> SEND 3     ACK 0xF0 TX_OK     ← 模块没被长发卡住
```

`MON` 逐字节确认:这两条命令之后模块**没有回任何字节**。是否真的在持续发射,本次没有观察到(需要看接收器),**记为未验证**。

## 7 一次未能复现的异常

学习遥控器教学期间,`INFO` 的 `stray` 从 3 涨到 72(69 个非帧字节),同时 `frames` 比打印行数多 2。
之后正常按两个遥控器 5 次,`stray` 保持不变,每帧都是完整 8 字节。

- 最可能:教学现场有非 1527/非 315M 的突发(或两台遥控器同时发送)被模块切成碎片输出。
- 影响:解析器把这类字节计入 `stray`(可见失败),没有误判成帧。
- 处理:记录,不修 —— 没有原始字节就改代码只会制造假修复。
